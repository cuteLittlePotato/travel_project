## 一、通用约定

### 1.1 基础路径

| 类型 | 前缀 | 说明 |
|------|------|------|
| C 端接口 | `/api/v1/` | 普通用户访问 |
| B 端接口 | `/api/v1/admin/` | 管理员访问 |

**路由分流**（见架构文档 2.1）：

| 路径 | 目标 |
|------|------|
| `/api/*` | FastAPI |
| `/admin/*` | B 端静态文件 |
| `/*` | Next.js（C 端 SSR） |

**版本兼容策略**：

| 变更类型 | 是否升版本 | 说明 |
|---|---|---|
| 新增响应字段 | ❌ 不升版 | 客户端应忽略未知字段 |
| 新增可选请求参数 | ❌ 不升版 | 老客户端不受影响 |
| 新增枚举值 | ❌ 不升版 | 客户端需容忍未知枚举值 |
| 修改字段类型 | ✅ 升 `v2` | 破坏性变更 |
| 删除字段 | ✅ 升 `v2` | 破坏性变更 |
| 改变参数或字段语义 | ✅ 升 `v2` | 破坏性变更 |
| 修改接口路径 | ✅ 保留旧路径或升 `v2` | — |

**约定**：
- 同一大版本内**字段只增不删**
- 破坏性变更需跨大版本，且旧版本保留至少 6 个月
- 前端两种客户端（Next.js C 端、Vite B 端）与后端同版本迭代，升级阻力小

### 1.2 认证方式

| 项 | 规则 |
|---|---|
| Token 类型 | JWT |
| 传递方式 | `Authorization: Bearer <token>` |
| Access Token 有效期 | 30 分钟 |
| Refresh Token 有效期 | 7 天 |
| C 端 Token | `access_token` / `refresh_token`，载荷 `user_type: "user"` |
| B 端 Token | `access_token` / `refresh_token`，载荷 `user_type: "admin"` |
| 隔离 | C 端 Token 不可访问 B 端接口，反之亦然 |

### 1.3 统一响应结构

**成功响应**：

```json
{
  "code": 0,
  "message": "ok",
  "data": { }
}
```

**失败响应**：

```json
{
  "code": 11002,
  "message": "该账号已被封禁",
  "data": null
}
```

**HTTP 状态码映射**：

| 场景 | HTTP | 业务码 |
|------|------|--------|
| 成功获取 | 200 | 0 |
| 创建成功 | 201 | 0 |
| 删除成功（无返回体） | 204 | — |
| 参数校验失败 | 400 | 10001 |
| 未登录 / Token 失效 | 401 | 11001 |
| 无权限 | 403 | 25001 |
| 资源不存在 | 404 | 模块专属码 |
| 资源冲突 | 409 | 模块专属码 |
| 额度超限 | 429 | 23001 |
| 服务端错误 | 500 | 10002 |

**参数校验失败详情**：

```json
{
  "code": 10001,
  "message": "参数校验失败",
  "data": {
    "errors": [
      { "field": "phone", "reason": "手机号格式不正确" },
      { "field": "password", "reason": "密码长度需在 8-32 位之间" }
    ]
  }
}
```

### 1.8 运维探针

供容器 healthcheck、Nginx 健康检查、K8s 探针使用。**不对外提供业务能力**，
前端业务代码不应调用。路径**不带版本前缀**，保证升级 API 版本时探针地址不变。

#### 1.8.1 存活探针

```
GET /api/health
```

只判断进程存活，**不探测外部依赖**。外部服务故障时不影响本接口返回成功，
避免依赖级联失败导致容器被反复重启。

**认证**：无需

**响应 200**：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "status": "ok"
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | string | 固定为 `ok` |

#### 1.8.2 就绪探针

```
GET /api/health/ready
```

探测全部外部依赖。**始终返回 HTTP 200**，通过 `status` 字段表达是否就绪——
探针的价值在于故障时给出逐项诊断，自身不应因依赖故障而失败。

**认证**：无需

**响应 200（全部就绪）**：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "status": "ready",
    "dependencies": {
      "postgres": true,
      "redis": true,
      "milvus": true,
      "neo4j": true,
      "elasticsearch": true,
      "minio": true
    }
  }
}
```

**响应 200（部分不可用）**：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "status": "degraded",
    "dependencies": {
      "postgres": true,
      "redis": true,
      "milvus": false,
      "neo4j": true,
      "elasticsearch": true,
      "minio": true
    }
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | string | `ready` = 全部可用；`degraded` = 至少一项不可用 |
| `dependencies` | object | 依赖名 → 是否可用（bool） |

**依赖项说明**：

| 键 | 对应服务 | 探测方式 |
|---|---|---|
| `postgres` | PostgreSQL | `SELECT 1` |
| `redis` | Redis | `PING` |
| `milvus` | Milvus | `list_collections()` |
| `neo4j` | Neo4j | `RETURN 1` |
| `elasticsearch` | Elasticsearch | `ping()` |
| `minio` | MinIO | `bucket_exists()` |

**超时策略**：单项探测超时 5 秒，超时记为不可用，不阻塞整体响应。

**与业务降级的关系**：探针报告 `degraded` 不代表服务对外不可用。
按架构 §1.6 决策 3，Redis 不可用时业务降级为直读 PostgreSQL，服务仍可正常工作。

## 三、M01 用户与账户

### 3.1 发送验证码

`POST /api/v1/auth/verification-codes`

**用途**：注册、登录、找回密码时发送验证码。

**请求体**：

| 字段 | 类型 | 必填 | 校验 | 说明 |
|------|------|------|------|------|
| target | string | 是 | 手机号或邮箱格式 | 接收目标 |
| scene | string | 是 | `register` / `login` / `reset_password` | 验证码场景 |

**响应**：

```json
{
  "code": 0,
  "message": "ok",
  "data": { "expires_in": 300 }
}
```

**业务规则**：
- 同目标 60 秒内不可重复发送
- 同目标每日最多 5 次
- 验证码有效期 5 分钟
- 错误码：`10003` 发送过于频繁（HTTP 429）

---

### 3.2 注册

`POST /api/v1/auth/register`

**请求体**：

| 字段 | 类型 | 必填 | 校验 | 说明 |
|------|------|------|------|------|
| target | string | 是 | 手机号或邮箱格式 | 注册标识 |
| verify_code | string | 是 | 6 位数字 | 验证码 |
| password | string | 是 | 8-32 位，含字母与数字 | 密码 |
| nickname | string | 否 | 1-50 字符 | 昵称，默认取 target 前缀 |

**响应**（HTTP 201）：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "user_id": "018f...",
    "access_token": "...",
    "refresh_token": "...",
    "expires_in": 1800
  }
}
```

**业务规则**：
- 手机号/邮箱已注册 → `11003`（HTTP 409）
- 验证码错误或过期 → `11004`
- 注册成功自动创建 `user_profile`、`user_setting`

---

### 3.3 密码登录

`POST /api/v1/auth/login`

**请求体**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| target | string | 是 | 手机号、邮箱或用户名 |
| password | string | 是 | 密码 |

**响应**：同注册

**业务规则**：
- 账号不存在 → `11005`（HTTP 404）
- 密码错误 → `11006`（HTTP 401）
- 账号封禁 → `11002`（HTTP 403）
- 账号注销 → `11007`（HTTP 403）
- 同一账号 5 次密码错误锁定 15 分钟 → `11008`

---

### 3.4 验证码登录

`POST /api/v1/auth/login-by-code`

**请求体**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| target | string | 是 | 手机号或邮箱 |
| verify_code | string | 是 | 验证码 |

**响应**：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "user_id": "018f...",
    "access_token": "...",
    "refresh_token": "...",
    "expires_in": 1800,
    "is_new_user": true
  }
}
```

**业务规则**：
- **未注册的 target 自动注册并登录**
- 响应中的 `is_new_user` 标识是否为本次自动创建，前端可据此展示引导
- **自动注册的昵称规则**：
  - 手机号：脱敏前缀 + 随机后缀，如 `138***a3f2`
  - 邮箱：用户名部分 + 随机后缀，如 `user_a3f2`
  - 脱敏规则：手机号保留前 3 位，中间用 `***` 替代
  - 随机后缀：4 位十六进制字符
  - 若生成的昵称冲突，重新生成随机后缀（最多重试 3 次）
- 自动注册的账号**无密码**，用户可通过「修改密码」接口设置
- 验证码错误或过期 → `11004`

---

### 3.5 第三方登录

`POST /api/v1/auth/oauth-login`

**请求体**：

| 字段 | 类型 | 必填 | 说明 |

### 3.7 登出

`POST /api/v1/auth/logout`

**请求头**：`Authorization: Bearer <token>`

**响应**：HTTP 204

**业务规则**：**全端登出**——使该用户所有设备上的 Refresh Token 失效

**实现方式（token 版本号）**：

```
user 表新增 token_version 字段（INTEGER，默认 0）
  ↓
JWT payload 携带 token_version
  ↓
每次校验 Token 时比对：payload.token_version == user.token_version
  ↓
登出 / 改密 / 封禁 → user.token_version 自增
  ↓
所有已签发的 Token 立即失效
```

**为什么用 token 版本号而非黑名单**：
- 无需存储每一条 Refresh Token，不新增表
- 无需定期清理过期黑名单
- 校验开销是「一次数据库查询」（可缓存到 Redis）

**说明**：这意味着**不支持单端登出**。用户在多设备登录时，任一端登出会导致所有端退出。若后续需要单端登出，需新增 Refresh Token 存储表。

### 3.8 获取当前用户资料

`GET /api/v1/users/me`

**请求头**：`Authorization: Bearer <token>`

**响应**：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": "018f...",
    "username": "user001",
    "nickname": "旅行者",
    "avatar_url": "https://...",
    "gender": "secret",
    "region_code": "110000",
    "status": "active",
    "created_at": "2026-01-15T08:00:00Z",
    "bindings": [
      { "provider": "phone", "provider_uid": "138****8888", "is_primary": true }
    ]
  }
}
```

**业务规则**：
- `provider_uid` 需脱敏（手机号中间四位打码、邮箱部分打码）
- 不返回 `credential`（密码哈希）

### 5.4 发送消息（SSE 流式）★核心接口

`POST /api/v1/chat/sessions/{session_id}/messages`

**请求头**：

| 头 | 值 |
|---|---|
| Authorization | Bearer &lt;token&gt; |
| Accept | text/event-stream |

**请求体**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| content | string | 是 | 用户消息，1-4000 字符 |
| show_thinking | boolean | 否 | 是否推送思考过程，默认 `true` |
| model_id | UUID | 否 | 临时切换模型（仅本会话生效） |

**响应**：`text/event-stream`

**SSE 事件类型**：

| event | 触发时机 | data 结构 |
|---|---|---|
| `intent` | 意图识别完成 | `{"intent":"trip_planning","confidence":0.98}` |
| `thinking` | 思考过程（`show_thinking=true` 时） | `{"text":"需要先检索北京的历史文化景点"}` |
| `tool_call` | 调用工具 | `{"tool":"rag_retrieve","args":{"query":"北京 历史文化"}}` |
| `tool_result` | 工具返回 | `{"tool":"rag_retrieve","result_count":12}` |
| `token` | 回答增量文本 | `{"text":"故宫"}` |
| `plan_card` | 方案卡片（结构见下方） | `{"candidates":[...],"recommended_candidate_id":"..."}` |
| `interaction` | 需要用户选择 | `{"interaction_id":"...","interaction_type":"plan_selection","payload":{...}}` |
| `citation` | 引用来源 | `{"index":1,"source":"故宫游览指南.pdf","page":3}` |
| `error` | 流式过程中的错误 | `{"code":23001,"message":"额度已用尽"}` |
| `done` | 结束 | `{"message_id":"...","usage":{"input_tokens":1200,"output_tokens":350}}` |
| `ping` | 心跳（每 15 秒） | `{}` |

**完整事件流示例**：

```
event: intent
data: {"intent":"trip_planning","confidence":0.98}

event: thinking
data: {"text":"用户需要北京3日游方案，先检查必要信息"}

event: interaction
data: {"interaction_id":"...","interaction_type":"requirements","payload":{"missing":["budget"],"prompt":"您的预算大概多少？","allow_custom":true}}

event: ping
data: {}

... (等待用户通过 5.5 接口提交选择)

event: thinking
data: {"text":"预算3000元，开始检索景点"}

event: tool_call
data: {"tool":"rag_retrieve","args":{"query":"北京 历史文化 景点"}}

event: tool_result
data: {"tool":"rag_retrieve","result_count":12}

event: plan_card
data: {"candidates":[{"id":"...","type":"economy","title":"经济型","total_budget":"2500.00"},...]}

event: interaction
data: {"interaction_id":"...","interaction_type":"plan_selection","payload":{"candidates":[...]}}

event: done
data: {"message_id":"...","usage":{"input_tokens":3200,"output_tokens":850}}
```

**`plan_card` 事件的完整结构**：

```json
{
  "candidates": [
    {
      "id": "018f...",
      "candidate_type": "economy",
      "title": "经济型",
      "total_budget": "2500.00",
      "attraction_count": 5,
      "accommodation_level": "经济型酒店",
      "transport_level": "公共交通",
      "dining_level": "快餐小吃",
      "recommend_score": 4.2,
      "highlights": ["预算友好", "覆盖经典景点"]
    },
    {
      "id": "018f...",
      "candidate_type": "standard",
      "title": "标准型",
      "total_budget": "3000.00",
      "attraction_count": 7,
      "accommodation_level": "舒适型酒店",
      "transport_level": "公交+打车",
      "dining_level": "特色餐厅",
      "recommend_score": 4.8,
      "highlights": ["最符合您的需求"]
    }
  ],
  "recommended_candidate_id": "018f..."
}
```

**字段说明**：

| 字段 | 说明 |
|---|---|
| `candidates[].id` | 方案 ID，与 `plan_candidate.id` 对应 |
| `candidate_type` | `economy` / `standard` / `comfort` / `custom` |
| `total_budget` | 总预算，字符串形式的金额 |
| `recommend_score` | 推荐评分（0-5） |
| `highlights` | 方案亮点文案，供前端展示 |
| `recommended_candidate_id` | 系统推荐的首选方案，前端可高亮标记 |

**与 6.7 方案对比接口的关系**：`plan_card` 事件与 `GET /api/v1/plans/{plan_id}/candidates/compare` 返回结构一致，前者用于流式推送，后者用于主动查询。

**业务规则**：
- **连接建立前校验**：未登录 → 401；会话不存在 → 404；额度超限 → 429（不建立 SSE）
- **流式过程中错误**：通过 `error` 事件推送，随后关闭连接
- **心跳**：每 15 秒发 `ping`，防止代理层断开
- **超时**：Agent 执行超过 5 分钟无事件 → 推送 `error` 并关闭
- **连接断开不影响流程**：状态已落库，用户重新进入会话可通过 `pending_interaction` 恢复
- **额度扣减**：模型调用成功后实时扣减，事件流中不暴露剩余额度

- 投递 Celery 任务，初始状态 `queued`

### 17.3 Q1：验证码登录是否自动注册（已解决）

**决策**：**自动注册**。

**理由**：
- 国内主流 App（微信、美团、携程等）普遍采用「验证码登录即注册」，用户已习惯
- 需求文档 2.1.1 中验证码是主要注册途径
- 降低注册门槛，提升转化率
- 「注册」接口仍保留，用于需要设置密码的场景

**昵称生成规则**：

| 场景 | 规则 | 示例 |
|---|---|---|
| 手机号 | 脱敏前缀 + 随机后缀 | `13812345678` → `138***a3f2` |
| 邮箱 | 用户名部分 + 随机后缀 | `user@qq.com` → `user_a3f2` |

- 脱敏：手机号保留前 3 位，中间用 `***` 替代
- 随机后缀：4 位十六进制字符
- 冲突重试：最多 3 次
- 自动注册账号无密码，可通过「修改密码」接口设置

**响应新增字段**：`is_new_user`（boolean），标识是否为本次自动创建，前端可据此展示引导。

### 17.4 Q2：登出是单端还是全端（已解决）

**决策**：**全端登出**。

**实现方式：token 版本号**

`user` 表新增 `token_version` 字段（INTEGER，默认 0）：

```
JWT payload 携带 token_version
  ↓
每次鉴权比对：payload.token_version == user.token_version
  ↓
以下操作触发 token_version 自增：
  · 用户登出
  · 修改密码
  · 账号被封禁
  · 管理员强制下线
  ↓
所有已签发 Token 立即失效
```

**为什么用 token 版本号而非黑名单表**：
- 无需存储每一条 Token，不新增表
- 无需定期清理过期黑名单
- 校验开销是一次数据库查询（可缓存 Redis）

**取舍**：不支持单端登出。多设备登录时，任一设备登出会导致全部退出。若后续需要单端登出，需新增 Refresh Token 存储表（含 `device_id`）。

**数据库变更**：

| 表 | 变更 |
|---|---|
| `user` | 新增 `token_version INTEGER NOT NULL DEFAULT 0` |

### 17.6 Q5：同名文件上传策略（已解决）

**决策**：**完全覆盖，不保留历史版本**。

**覆盖动作**：

```
上传同名文件
  ↓
1. 删除旧文档的 kb_chunk 记录
2. 删除旧文档在 Milvus 的向量
3. 删除旧文档在 ES 的索引
4. 删除旧文档在 MinIO 的原始文件
5. 删除旧 kb_document 记录
6. 创建新的 kb_document 记录，重新走完整链路
```

**覆盖后旧版本不可恢复**，运营需重新上传原始文件。

**理由**：
- 需求文档 2.2.4.6 已明确「自动覆盖」
- 知识库文档通常有原始来源，误覆盖后重新上传即可
- 保留历史版本会导致 `kb_document` 表持续膨胀，查询需额外过滤

**对数据库的影响**：无变更（`kb_document` 表结构不变）。

### 17.7 Q6：PG 与 Neo4j 双写策略（已解决）

**决策**：**PG 优先，Neo4j 异步补偿**。

**写入流程**：

```
创建 / 更新 / 删除图谱实体
  ↓
1. 写 PG（事务提交，立即返回响应）
  ↓
2. 投递 Celery 任务：sync_entity_to_neo4j
  ↓
3. Worker 消费，写 Neo4j
  ├─ 成功 → 完成
  └─ 失败 → 重试（最多 3 次，指数退避：1s / 5s / 30s）
              ↓
          仍失败 → 标记为「同步失败」+ 告警通知管理员
  ↓
4. 每日 00:30 全量对账任务扫描差异并修复
```

**为什么不采用同步双写**：
- PG 是权威数据源（架构已确认），业务写入应以 PG 为准
- 与「名称修改用异步同步」的既有策略一致
- Neo4j 暂时不可用时，业务仍可继续（先建人物，图谱稍后出现）

**接口层的体现**：

| 场景 | 行为 |
|---|---|
| 创建实体 | 立即返回，响应含 `graph_sync_status: "pending"` |
| 查询实体 | 返回 `graph_sync_status` 当前状态 |
| 同步失败 | `graph_sync_status: "failed"`，B 端列表可筛选显示异常项 |
| 手动重试 | 提供接口触发重新同步 |

**对数据库的影响**：需在实体表新增同步状态字段。

| 表 | 新增字段 |
|---|---|
| `kg_person` | `graph_sync_status VARCHAR(20) NOT NULL DEFAULT 'synced'`<br>`graph_sync_error TEXT` |
| `kg_event` | 同上 |
| `kg_culture` | 同上 |

字段取值：`pending`（待同步）/ `synced`（已同步）/ `failed`（同步失败）

**`graph_sync_error` 的用途**：记录最后一次失败原因（如「Neo4j 连接超时」），同步成功后清空。运营可在 B 端看到具体原因，无需查服务端日志。

**新增接口**（2 个）：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/admin/knowledge-graph/entities/{type}/{id}/sync` | 手动触发重新同步 |
| GET | `/api/v1/admin/knowledge-graph/sync-failures` | 查询同步异常实体 |

**接口总数影响**：M10 从 18 → 20，总计 175 → 177。
