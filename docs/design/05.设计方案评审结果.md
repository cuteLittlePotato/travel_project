## 三、需要决策的问题

### 🔴 3.1 架构缺陷：M17 与 M12 的同层依赖

**问题描述**：

架构文档 3.2 节定义了依赖规则：

> **同级解耦**：同层模块之间不直接依赖，通过下层或事件解耦

但 3.3 节的模块职责表中：

| 模块 | 架构位置 | 主要依赖 |
|---|---|---|
| M12 模型管理 | **基础层** | - |
| M17 推荐引擎 | **基础层** | M07、**M12** |

M17 与 M12 同处基础层，M17 依赖 M12 生成推荐理由（需求已确认「推荐理由由模型生成」），**违反了同层解耦原则**。

**影响**：
- 若后续将推荐引擎拆分为独立服务，会因依赖 M12 而耦合
- 架构文档自身规则与实际设计矛盾

**三个解决方案**：

- **A. 调整 M17 的层级归属**：将 M17 从「基础层」上移到「能力层」，与 M06/M07/M08 并列
  - 理由：推荐引擎本质上是一项「能力」，服务于 M02 景点内容，与 Agent 引擎同级
  - 影响：需修改架构文档的模块分层图与职责表
  - 代价：改动小，但需重新审视 M17 与 M06/M07/M08 的关系

- **B. 允许特例，修改依赖规则**：在架构文档中注明「M17 因需调用模型生成推荐理由，特例允许依赖 M12」
  - 理由：务实，M17 调用 M12 是合理的业务需求
  - 影响：规则表述需放宽
  - 代价：开了特例先河，后续可能出现更多例外

- **C. 解耦：M17 通过事件获取推荐理由**：M17 只负责「算出推荐哪个景点」，推荐理由的生成由 M06 异步完成并回写
  - 理由：彻底解耦，符合事件驱动架构
  - 影响：需新增事件机制与异步流程
  - 代价：复杂度显著增加，且推荐理由需与推荐结果同步展示，异步可能不满足体验

**评审建议：A**。

理由：M17 的职责（热度计算、推荐策略、推荐理由生成）本质上是「能力」而非「基础数据」，归入能力层更准确。且它依赖 M07（记忆）也印证了这一点——记忆服务在能力层。

**请选择 A / B / C。**

### 🟠 3.2 需求文档与设计的语义偏差：热门景点排行榜的排序依据

**问题描述**：

需求文档 2.2.7 数据看板中写：
> 热门景点排行（基于浏览量、加入计划次数）

但数据库设计与 API 设计中，`hot_attractions` 的排序依据是 `final_popularity`（最终热度值 = 基础权重 × 0.6 + 行为得分 × 0.4），而非单纯的浏览量或加入计划次数。

同时 API 文档 15.2 节写：
> `hot_attractions` 按 `final_popularity` 排序，取前 10

**这是否算偏离需求？**

两种理解：

- **A. 不算偏离**：`final_popularity` 的计算公式中已包含浏览量与加入计划次数（作为 `behavior_score` 的组成部分），因此「基于浏览量、加入计划次数」的意图已被满足
- **B. 算偏离**：需求明确要求「按浏览量 + 加入计划次数」排序，设计改成了综合热度，需修正为按这两个指标排序

**评审建议：A**。

需求文档 2.2.7 中的「基于浏览量、加入计划次数」应理解为「热度计算的输入组成」，而非「直接的排序字段」。同一份需求文档 2.1.2 首页热度排行也写「按热度值排序」，两处应统一为热度值。

但这是**需求层面的解释**，需要你确认。

**请选择 A / B。**

## 四、可优化的设计细节（建议项，不影响正确性）

### 4.1 `attraction_category_relation` 缺少更新接口

**现状**：B 端如果要修改某景点的分类，只能「删除全部关联 → 重新添加关联」。

**建议**：提供批量设置接口：

```
PUT /api/v1/admin/attractions/{attraction_id}/categories
{ "category_ids": ["...", "..."] }
```

**整体替换语义**，避免多次调用。

**是否需要**：此项影响开发便利性，但不影响功能完整性。

---

### 4.2 知识库文档列表缺少「按入库参数筛选」

**现状**：数据库设计了 `indexed_meta` 字段，API 8.9 返回了 `is_outdated_params`，但无法**筛选出所有使用旧参数的文档**。

**建议**：为 `GET /api/v1/admin/knowledge-bases/{kb_id}/documents` 增加查询参数 `is_outdated_params: boolean`。

**理由**：切分参数变更后，运营需要快速找到所有旧参数文档并批量重建。

---

### 4.3 `user_event` 的 `event_type` 缺少 CHECK 约束

**现状**：SQL 中 `user_event.event_type` 定义为 `VARCHAR(50) NOT NULL`，没有 CHECK 约束。

**对比**：其他枚举字段（如 `process_status`、`notification_type`）都有 CHECK。

**建议**：增加 CHECK 约束，或者在注释中明确列出所有合法值。

**注意**：埋点事件类型可能频繁新增，加 CHECK 会导致每次加事件都要改表。**当前设计（无 CHECK + 注释说明）是合理取舍**，此项仅记录，不建议强改。

---

### 4.4 缺失的索引：`trip_plan` 按状态和日期的复合查询

**现状**：已有 `idx_tripplan_status_dates (status, start_date, end_date)`。

**检查**：定时任务需要查询「`status='pending'` 且 `start_date = today`」的记录。

**结论**：现有索引可覆盖（`status` 前缀 + 日期范围扫描）。**无需调整**。

---

### 4.5 API 文档中 `plan_card` 事件的结构未定义

**现状**：SSE 的 `plan_card` 事件返回 `{"candidates":[...]}`，但 `candidates` 数组的内部结构未在事件定义处说明。

**建议**：明确 `plan_card` 事件的完整结构，可参考 6.7 方案对比接口的响应格式。

### 6.3 3.2 的判定依据（已确认）

需求文档 2.2.7 数据看板中写「热门景点排行（基于浏览量、加入计划次数）」，而设计使用 `final_popularity`（综合热度值）。

**判定为「不算偏离」的理由**：

1. `final_popularity = base_popularity × 0.6 + behavior_score × 0.4`
2. `behavior_score` 的计算已包含浏览量、点击量、加入计划次数、评分
3. 同一份需求文档 2.1.2 首页热度排行也写「按热度值排序」，两处应统一
4. 「基于 X、Y」应理解为「X、Y 是计算输入」，而非「直接按 X、Y 排序」

**结论**：设计与需求意图一致，无需修改。
