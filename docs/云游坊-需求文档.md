# 云游坊 - 旅游推荐与规划系统需求文档

## 1. 项目概述

### 1.1 项目简介
云游坊是一个面向旅游爱好者和计划旅行用户的智能旅游推荐与规划平台。系统通过大语言模型（LLM）驱动的对话交互，为用户提供个性化的景点推荐和全自动旅游行程规划服务。

### 1.2 目标用户

**C 端用户（互联网旅游用户）**
- **有旅游计划的用户**：需要获取景点信息、制定详细行程
- **旅游爱好者**：浏览发现景点、记录旅行足迹、获取个性化推荐
- **典型使用场景**：规划假期旅行、查询目的地信息、管理多个旅游计划、记录旅行回忆

**B 端用户（平台运营人员）**
- **内容运营**：管理景点、餐饮、酒店等基础数据
- **用户运营**：查看用户行为、优化推荐策略
- **数据分析**：通过看板了解平台运营状况，支持决策

### 1.3 核心价值
- 智能对话式旅游规划，降低行程制定门槛
- 地理位置优化的行程安排，提升旅行体验
- 个性化推荐，基于用户偏好和行为
- 旅行足迹沉淀，构建用户旅行档案

## 2. 功能架构

### 2.1 C 端功能模块

#### 2.1.1 用户认证
- **注册登录方式**：
  - 手机号 + 验证码注册
  - 邮箱 + 验证码注册
  - 第三方登录（微信、支付宝、微博等）
  - 支持多种登录方式绑定到同一账户

#### 2.1.2 首页与景点浏览
- **热度排行展示**：
  - 按热度值排序显示景点列表
  - 显示热度数值
  - 鼠标悬停显示推荐理由
  
- **分类浏览**：
  - **按类型**：历史人文（故宫、大雁塔）、自然景色（张家界、九寨沟）等
  - **按省份/城市**：北京、上海等
  - 多级分类展示（省份 → 城市 → 景点）

- **景点详情页**：
  - 基础信息：名称、地理位置、分类
  - 详细介绍、图片展示
  - 门票价格、开放时间
  - 建议游玩时长、最佳游览季节
  - 交通指南、联系方式

#### 2.1.3 智能对话窗口

##### 2.1.3.1 功能定位
智能对话窗口是云游坊的核心交互入口，通过 AI Agent 为用户提供智能的旅游规划和咨询服务。系统采用大语言模型驱动，结合多种知识检索能力和工具调用能力，提供上下文感知的对话体验。

##### 2.1.3.2 Agent 整体架构

**架构模式**：混合架构（状态机 + Plan-and-Execute + ReAct）

```
用户输入（SSE 流式推送）
  ↓
[意图识别与路由] 
  - 方式：LLM 分类（提示词工程）
  - 置信度阈值：>80% 直接执行，70-80% 确认，<70% 反问
  ↓
┌─────────────────┬───────────────────┐
│                 │                   │
│  行程规划意图    │   其他意图         │
│  （复杂状态机）  │  （简化流程）      │
│                 │                   │
│  6节点设计      │  Plan + ReAct     │
│  详细流程控制    │  快速响应         │
└─────────────────┴───────────────────┘
```

**关键特性**：
- ✅ **SSE 流式推送**：只在缺少关键信息时 interrupt（中断等待用户），其他时候持续输出
- ✅ **意图路由**：根据用户意图复杂度选择不同的处理流程
- ✅ **工具编排**：通过 MCP 协议统一调用各类工具

##### 2.1.3.3 支持的意图类型

| 意图类型 | 示例 | 处理流程 | 实现状态 |
|---------|------|---------|----------|

| **交通咨询** | "从机场到故宫怎么走？" | Plan + ReAct + 地图 API | ⚠️ 工具占位 |
| **天气咨询** | "北京下周天气怎么样？" | Plan + ReAct + 天气 API | ⚠️ 工具占位 |

**说明**：

##### 2.1.3.4 行程规划流程（状态机设计）

行程规划是最复杂的意图，采用 6 节点状态机流程：

**节点 1：信息收集（collect_requirements）**
```
目标：收集用户需求信息

必要信息：
- destination（目的地）
- days（天数）
- budget_per_person（预算）

可选信息：
- people_count（人数）
- departure_date（出发日期）
- interests（兴趣偏好）
- accommodation_level（住宿标准）
- dietary_preference（餐饮偏好）
- must_visit（必去景点）
- exclusions（排除项）

收集策略：
- 缺失 1-2 个信息：一次性询问所有缺失项
- 缺失 3 个以上：弹出表单快速填写
- 可选信息：直接使用长期记忆或默认值，不追问

示例对话：
用户："帮我规划北京的行程"
Agent："好的！为了更好地规划，请提供以下信息：
       1. 计划玩几天？
       2. 预算大概多少？"
用户："3天，预算3000"
→ 信息收集完成，进入下一节点
```

**节点 2：检索候选景点（retrieve_attractions）**
```
目标：根据需求检索合适的景点

检索策略：
- 数据库查询：按目的地、分类、价格筛选
- RAG 检索：查询知识库中的景点评价和攻略
- 并行执行，融合结果

输出：候选景点列表（20-50 个）
```

**节点 3：生成方案（generate_plans）**
```
目标：生成 2-3 个差异化旅游方案

生成策略：
1. 先生成"标准方案"（匹配用户预算）
2. 进入 ReAct 循环优化标准方案（最多 10 次）
   - 优化维度：预算精确匹配、景点合理性、路线优化、知识增强
   - 终止条件：LLM 判断"足够好" 或 达到 10 次上限
3. 基于标准方案派生其他方案：
   - 经济型：降级住宿/餐饮，减少非必要景点
   - 舒适型：升级住宿/餐饮，增加精品体验

差异化维度：
- 按预算分层（经济型 / 标准型 / 舒适型）
- 相同天数，不同价格区间

输出：2-3 个完整方案（JSON 格式）
```

**方案候选集的生命周期**：

| 阶段 | 处理 |
|------|------|
| 生成时 | 全部 2-3 个方案均保留 |
| 用户选中一个并保存后 | **未选中的方案仍然保留**，作为备选 |
| 存放位置 | 挂在对应行程下，作为「备选方案」 |
| 用户可否切回 | 可以，随时可查看或切换到其他备选方案 |

**节点 4：展示方案（present_plans）**
```
目标：以卡片式可视化方式展示方案

展示形式：
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│  💰 经济型       │  │ ⭐ 标准型 推荐   │  │  ✨ 舒适型       │
│  ¥2500/人       │  │  ¥3000/人       │  │  ¥4000/人       │
│                 │  │                 │  │                 │
│  📍5个景点      │  │  📍7个景点      │  │  📍5个景点      │
│  🏨经济酒店     │  │  🏨舒适酒店     │  │  🏨四星酒店     │
│  🍜快餐小吃     │  │  🍜特色餐厅     │  │  🍜品质美食     │
│                 │  │                 │  │                 │
│  [查看详情]     │  │  [查看详情]     │  │  [查看详情]     │
└─────────────────┘  └─────────────────┘  └─────────────────┘

核心对比维度（优先级排序）：
1. 总预算
2. 景点质量（5A/4A/口碑）
3. 住宿标准
4. 交通方式
5. 餐饮标准

方案详情包含：
- 每日景点列表 + 游玩时长 + 门票价格 + 开放时间
- 景点间交通方式 + 预计时间
- 用餐安排 + 餐厅推荐
- 住宿详情（酒店名称 / 位置 / 价格）
- 每日预算明细
- 每日时间轴（08:00-22:00 详细安排）
- 文化背景介绍（知识图谱链接）
- 游玩建议（拍照点 / 避坑提示）
- 备选方案（天气 / 限流应对）

用户交互：
- 用户点击查看详情
- Agent 询问："是否需要调整？"
```

**节点 5：处理调整意图（handle_adjustment）**
```
目标：识别用户是否需要调整方案

场景 1：用户满意
用户："就用方案 2 吧"
→ 保存方案，流程结束

场景 2：用户需要调整
用户："能把第二天的景山换成天坛吗？"
→ 进入节点 6（方案调整）

场景 3：用户想看其他方案
用户："还有别的方案吗？"
→ 返回节点 3，生成新方案
```

**节点 6：方案调整（adjust_plan）**
```
目标：支持用户对方案的全方位调整

支持的调整类型：

【景点层面】
- 增加景点："我还想去颐和园"
- 删除景点："不想去景山公园了"
- 替换景点："把景山换成天坛"
- 调整顺序："先去长城再去故宫"
- 调整时长："故宫多玩 1 小时"

【住宿层面】
- 更换酒店："换一个离景点更近的"
- 升降级："换成经济型酒店省钱"
- 指定品牌："我只住全季酒店"

【餐饮层面】
- 更换餐厅："不想吃全聚德"
- 调整预算："吃得简单一点"
- 菜系偏好："我不吃辣"

【交通层面】
- 更换方式："打车别坐公交"
- 调整时间："我想晚点出发"

【整体层面】
- 调整预算："预算降到 2500"
- 调整天数："改成 4 天 3 夜"
- 改变风格："改成深度游"

实现方式：
- 对话式调整 + 可视化编辑（混合式）
- 用户可以语音/文字描述需求
- 也可以点击界面上的编辑按钮

约束冲突处理：
场景 1：时间冲突
  用户："Day1 增加颐和园"
  Agent："颐和园需要 4 小时，Day1 时间不够，建议安排到 Day2"
  
场景 2：预算超支
  用户："把酒店换成四星级"
  Agent："升级四星酒店会超预算 1200 元，确认吗？"
  
场景 3：逻辑冲突
  用户："Day1 去长城，Day2 去故宫"
  Agent："长城距离市区远，Day1 去长城后 Day2 不太合理再回市区，
         建议长城安排在最后"

调整后处理：
Agent："调整完成，是否保存？
       [保存为新方案] [覆盖原方案]"
```

##### 2.1.3.5 其他意图流程（Plan + ReAct）

其他意图（景点咨询、知识探索、交通/天气/预订咨询）采用简化流程：

**Plan 阶段：制定执行计划**
```python
# 示例：用户问"故宫值得去吗？"

Agent 分析并制定计划：
Plan = [
    "步骤 1：查询数据库获取故宫基础信息",
    "步骤 2：如果信息不够，调用 RAG 检索评价",
    "步骤 3：如果还不够，调用 GraphRAG 查询文化价值",
    "步骤 4：整合信息生成回答"
]
```

**ReAct 循环执行**
```
循环 1：
  Thought（思考，结构化 Prompt）：
    {
      "current_task": "查询故宫基础信息",
      "should_execute": true,
      "action": "query_database"
    }
  
  Action（行动）：
    调用工具：query_database("故宫")
  
  Observation（观察）：
    返回结果："5A 景区，门票 60 元，开放时间 8:30-17:00"
  
  Thought（思考）：
    {
      "is_sufficient": false,  # 信息不够
      "reason": "只有基础信息，缺少评价性内容",
      "next_action": "rag_retrieve"
    }
  → 继续下一轮

循环 2：
  Thought：需要调用 RAG 查询评价
  Action：rag_retrieve("故宫 值得 评价")
  Observation："故宫是中国最著名的古建筑群，世界文化遗产..."
  Thought：
    {
      "is_sufficient": true,  # 信息足够
      "next_action": "finish"
    }
  → 结束循环，生成回答

最终回答：
"故宫非常值得去！它是中国最著名的古建筑群，世界文化遗产..."
```

**终止条件**：
- LLM 判断信息"足够好"
- 或达到 10 次循环上限

**达到上限时的处理**：
- 基于已有信息回答 + 标注"部分信息可能不完整，建议以官方信息为准"

##### 2.1.3.6 工具调用能力（MCP 协议）

Agent 可以调用以下工具，通过 **Model Context Protocol** 统一接口：

| 工具名称 | 功能 | 实现状态 | 失败处理 |
|---------|------|----------|----------|
| query_database | 查询结构化数据（景点/餐厅/酒店） | ✅ 实现 | 返回空结果 |
| rag_retrieve | RAG 检索知识库文档 | ✅ 实现 | 用通用知识兜底 |
| graphrag_query | GraphRAG 查询知识图谱 | ✅ 实现 | 查找间接关系 |
| call_map_api | 调用地图 API（路线/距离） | ⚠️ 占位 | 重试 3 次 → 降级 |
| call_weather_api | 调用天气 API | ⚠️ 占位 | 重试 3 次 → 降级 |
| call_booking_api | 调用预订 API | ⚠️ 占位 | 重试 3 次 → 降级 |
| calculate_route | 计算景点间路线 | ⚠️ 占位 | 降级为直线距离 |
| calculate_budget | 计算行程预算 | ✅ 实现 | - |
| search_web | 联网搜索实时信息 | ⚠️ 占位 | 用离线数据兜底 |
| generate_trip_plan | 调用行程规划算法 | ✅ 实现 | - |
| user_memory_query | 查询用户长期记忆 | ✅ 实现 | 使用默认值 |
| finish | 结束循环，生成回答 | ✅ 实现 | - |

**工具失败处理策略**：
- **超时**：重试最多 3 次 → 使用降级方案（如："抱歉，暂时无法查询交通信息，请稍后再试"）
- **空结果**：优化查询关键词 → 尝试其他工具 → LLM 通用知识兜底

##### 2.1.3.7 知识检索能力

Agent 支持三种检索方式的协同工作：

**检索策略（按问题类型）**

| 问题类型 | 示例 | 检索方式 | 说明 |
|---------|------|---------|------|
| **事实查询** | "故宫门票多少钱？" | 数据库 + RAG | 并行查询，优先数据库 |
| **描述性查询** | "故宫有什么值得看的？" | 数据库 + RAG | 并行查询，融合结果 |
| **关联推理** | "朱棣和故宫有什么关系？" | 数据库 + RAG | 并行查询 + GraphRAG 补充 |
| **多跳推理** | "康熙住过的地方附近有什么好吃的？" | GraphRAG + RAG | GraphRAG 多跳 → RAG 补充细节 |

**协同策略：并行检索**
```
同时调用：
- query_database()
- rag_retrieve()
- graphrag_query()（按需）

结果融合：
- 数据库：提供结构化事实
- RAG：提供详细描述和评价
- GraphRAG：提供关联信息和深度知识

由 LLM 整合生成最终回答
```

**结果融合规则**：

三路检索结果合并后，**按相关性统一排序**，不按来源分主次。

| 环节 | 规则 |
|------|------|
| 排序依据 | 交给重排序模型（Rerank）统一打分，而非各检索源自行返回的分数 |
| 平局处理 | 相关性相同时，按来源权威性排序：官方数据 > 知识库 > 通用知识 |
| 去重 | 相同内容仅保留相关性最高的一条 |

**检索参数**：

| 参数 | 默认值 | 是否可覆盖 |
|------|--------|-----------|
| top-k（返回切片数） | 5 | 知识库级可覆盖 |
| 相似度阈值 | 0.5 | 知识库级可覆盖 |

**质量控制与兜底（按序执行）**：

| 场景 | 处理 |
|------|------|
| RAG 返回为空或低于阈值 | 使用 LLM 通用知识兜底 |
| GraphRAG 查不到直接关系 | 查找间接关系并解释（如："朱元璋和故宫没有直接关系，故宫是他的儿子朱棣修建的"） |
| GraphRAG 连间接关系也查不到 | **① 先转 RAG 检索该实体**；**② RAG 仍无结果时，用模型通用知识回答并标注**「以下内容来自通用知识，非平台收录」 |
| 结果矛盾 | 选择来源最权威的（优先级：官方数据 > 知识库 > 通用知识） |

**来源标注**：
- 默认不显示来源
- 用户可点击 [💡 查看信息来源] 查看引用详情

##### 2.1.3.8 记忆系统

**短期记忆（会话内）**
```
ConversationContext = {
    "messages": [
        SystemMessage("历史对话摘要：用户想规划北京 3 日游..."),
        HumanMessage("最近 N 轮完整对话"),
        AIMessage("..."),  # 已包含工具调用结果
        # ...
    ]
}
```

**关键点**：
- ✅ 工具调用结果已融入 AIMessage，不单独维护
- ✅ 压缩策略：历史摘要 + 最新 N 轮完整对话
- ✅ 触发条件：达到模型上限的 70% 时压缩

**长期记忆（跨会话）**

存储范围：
1. **用户偏好**：
   - 兴趣偏好（历史文化 / 自然风光 / 美食购物等）
   - 预算水平（经济型 / 舒适型 / 豪华型）
   - 旅游风格（深度游 / 走马观花 / 休闲度假）
   - 体力要求、住宿偏好、餐饮偏好、出行方式偏好

2. **历史行为**：
   - 浏览过的景点
   - 收藏的景点 / 餐厅 / 酒店
   - 完成的行程（已去过的地方）
   - 对话中明确提到的"不喜欢"

3. **情境信息**：
   - 常同行人数（如：经常 2 人出行）
   - 出行频率（如：每季度一次）
   - 出行时间偏好（如：更喜欢周末 / 假期）
   - 出发地（如：常驻北京）

**记忆管理策略**：
- **有效期**：智能衰减（最近的偏好权重更高，旧的逐渐降权）
- **用户控制**：可查看，不可编辑（系统自动学习）
- **可见粒度**：以**结构化标签**形式展示，不展示原始推断依据

  示例：
  ```
  系统了解到的你的偏好：
  · 旅游类型：历史文化、自然风光
  · 预算水平：中等
  · 常驻地：北京
  · 常见同行人数：2 人
  ```
  
- **隐私合规**：仅用于个人体验，注销后立即删除
- **加载时机**：会话开始时全部加载

**工作记忆（规划流程中间状态）**

存储内容：
- 已收集的需求信息
- 候选景点列表
- 已生成的方案
- 用户选择的方案
- 调整历史

生命周期：
- 方案已保存：保留到会话结束（用户可能反悔）
- 用户中断后回来：继续之前的状态（无缝衔接）

##### 2.1.3.9 状态保存与会话恢复

**SSE 流式推送机制**
```
用户发送请求
  ↓
Agent 开始处理（流式输出）
  ↓
  ├─ 正常流程：持续输出，不等待用户
  └─ 需要关键信息：interrupt（中断，等待用户输入）
```

**关键特性**：
- ✅ 只在缺少关键信息时 interrupt（如：缺少目的地、天数、预算）
- ✅ 其他时候 Agent 持续推理输出，不关心用户是否在线
- ✅ 不需要传统的"会话超时"概念

**状态持久化**：
- **保存时机**：每轮对话后立即保存
- **保存内容**：
  - 消息链（完整对话历史）
  - 当前意图与流程状态
  - 工作记忆（规划中间状态）
  - ReAct 循环状态（如果正在执行）

**会话恢复体验**：
- 用户离开后回来：**无缝继续**，不提示中断
- 示例：
  ```
  10:00 用户："帮我规划北京 3 日游"
  10:05 Agent："请问您的预算？"
  10:06 用户离开
  10:30 用户回来："3000"
  Agent："好的，预算 3000 元。正在为您生成方案..."
  ```

**行程与会话解耦**：
```
重要设计：行程作为独立资源，不绑定会话

TripPlan（行程表）：
- plan_id: UUID
- user_id: UUID
- status: "planning" / "completed" / "archived"
- content: {...行程详情...}

Session（会话表）：
- session_id: UUID
- user_id: UUID
- messages: [...对话历史...]
- current_operation: "planning" / "querying" / ...

优势：
- 用户可以在任何会话中查询"我有哪些正在规划的行程？"
- 可以在新会话中继续编辑某个行程
- 可以同时规划多个行程
```

**并发编辑约束**：

同一行程在同一时间**只允许一个会话进行编辑**，其他会话对该行程只读。

| 场景 | 行为 |
|------|------|
| 会话 A 正在编辑行程 X | 该行程进入「编辑锁定」状态 |
| 会话 B 尝试编辑行程 X | 提示「该行程正在其他会话中编辑，当前为只读模式」 |
| 会话 A 结束编辑 / 关闭会话 | 锁释放，其他会话可编辑 |

**说明**：此约束避免多会话同时修改同一行程导致数据冲突。

#### 2.1.4 旅游计划管理
- **全自动行程生成**：
  - 用户输入：目的地、出发/结束时间、预算、偏好等
  - 系统自动生成：
    - 每日景点安排（具体时间段）
    - 餐厅推荐（早中晚餐）
    - 酒店住宿建议
    - 交通安排（城际+市内）
  - **地理位置优化**：
    - 基于地图 API 计算景点间距离
    - 优化游览顺序，减少往返路程
    - 考虑景点开放时间约束

- **交通安排**：
  - **城际交通**：通过 MCP 工具实时查询（如"北京-上海：飞机2小时/高铁5小时，价格区间"）
  - **市内交通**：基于地图 API 计算距离和预估时间，推荐交通方式
  - **景区交通**：从 B 端数据库查询（如"九寨沟观光车"、"张家界索道"）

- **计划状态流转**：
  | 状态 | 流转规则 | 编辑权限 |
  |------|---------|---------|
  | **规划中** | 新创建的计划 | 完全可编辑、可删除 |
  | **待进行** | 用户手动点击"确认计划" | 可编辑、可取消（回到规划中） |
  | **进行中** | 到达出发日期自动流转 | 可微调（换餐厅、调整顺序），不可取消 |
  | **已完成** | 结束日期后自动提醒，用户手动确认 | 不可修改行程内容，可补充 UGC |

- **计划列表管理**：
  - 按状态分类显示：规划中、待进行、进行中、已完成
  - 支持搜索、筛选、排序

#### 2.1.7 景区知识图谱

**功能描述**：构建景区知识图谱，存储景点与历史人物、历史事件、文化元素、地理位置等实体之间的关系，用于增强智能对话、景点详情展示和个性化推荐。

**核心实体类型**：
- **景点实体**：名称、别名、类型、等级、坐标、历史背景等
- **地理区域**：国家、省份、城市、区县及其层级关系
- **历史人物**：姓名、朝代、职业、代表作、生卒地等
- **历史事件**：事件名称、时间、地点、参与者、历史意义
- **文化元素**：建筑风格、艺术形式、民俗活动、地方特产等
- **景点类别**：自然景观（山岳、湖泊、森林等）、人文景观（古建筑、寺庙、博物馆等）
- **周边设施**：餐厅、酒店、交通站点、商店等
- **交通方式**：公交、地铁、自驾路线、步行路径等

**关系类型**：
- **地理关系**：
  - 位于关系（景点 → 城市 → 省份）
  - 附近关系（景点A ← 距离X公里 → 景点B）
  - 包含关系（景区 → 子景点，如故宫 → 太和殿）
  - 连通关系（景点间的交通连接）

- **历史文化关系**：
  - 相关人物（景点 → 历史人物，如苏州园林 → 唐寅）
  - 建造者（景点 → 人物/朝代，如长城 → 秦始皇）
  - 事件发生地（历史事件 → 景点，如西安事变 → 华清池）
  - 代表文化（景点 → 文化元素，如故宫 → 明清建筑风格）

- **游客行为关系**：
  - 适合人群（景点 → 人群类型，如迪士尼 → 家庭亲子）
  - 最佳时节（景点 → 季节/月份）
  - 推荐组合（景点A → 景点B，基于用户行为挖掘）
  - 相似景点（基于特征相似度）

- **服务关系**：
  - 提供服务（景点 → 设施）
  - 可达性（景点 → 交通方式）

**应用场景**：

1. **智能对话增强**
   - 问答能力：回答"故宫是谁建造的？""故宫附近有什么景点？"等问题
   - 深度讲解：基于知识图谱提供景点的历史背景、文化内涵等深度信息
   - 关联推荐：根据对话上下文推荐相关景点

2. **景点详情页展示**
   - **知识图谱可视化**：
     - 以可交互的图谱形式展示当前景点的关系网络
     - 节点类型：景点、人物、事件、文化元素等
     - 边类型：建造者、相关人物、附近景点、相似景点等
     - 交互方式：点击节点查看详情、点击边查看关系说明
   
   - **关联内容展示**：
     - 相关历史人物卡片（如故宫 → 朱棣、康熙、乾隆）
     - 历史事件时间线（如华清池 → 唐玄宗与杨贵妃、西安事变）
     - 建筑风格/文化特色标签
     - 附近景点推荐（基于地理关系）
     - 相似景点推荐（基于类型/风格相似度）

3. **智能推荐**
   - **关系推荐**：用户喜欢故宫 → 推荐同朝代的明十三陵
   - **路径推荐**：基于地理邻近关系规划一日游路线
   - **深度游推荐**：推荐同一文化主题的系列景点

4. **行程规划优化**
   - 考虑景点间的地理关系优化路线
   - 根据文化主题组织连贯的行程
   - 避免相似景点重复安排

**数据来源**：
- **运营人员录入**：在 B 端管理后台手动维护实体和关系
- 初期数据规模：核心热门景点及其主要关系
- 数据扩展：逐步补充完善

**后续迭代方向**：
- 引入自动化数据提取（从百科、旅游网站爬取）
- 利用 AI 从文本中抽取实体和关系
- 扩展更多实体类型和关系类型
- 优化图谱可视化效果和交互体验

#### 2.1.8 发现页

**功能定位**：为用户提供景点内容之外的其他探索入口，承接「浏览」之外的发现需求。

##### 2.2.4.2 文件上传与管理

**设计原则：配置归属知识库，上传只负责传文件**

一个知识库对应一个 Milvus Collection，即**一个向量空间**。因此切分参数、分割符、向量化模型、重排序模型等所有影响「向量如何产生」的配置，必须由知识库统一持有，不能随单次上传而变。否则同一 Collection 内会混入不同模型或不同粒度的向量，语义距离不可比较，检索会静默失效。

由此得出：
- **上传界面不再包含任何配置项**，只做文件选择与确认
- **每个知识库提供独立的「配置」入口**，集中管理切分与模型参数

##### 2.2.4.2.1 文件归一化链路

**设计目标**：将异构格式统一归一化为 Markdown 后，再进行结构感知切分和向量化。整个链路对普通用户完全无感，运营人员只需跟踪每个文件的状态。

**完整链路**：

```
原始文件上传
  ↓
[步骤1] 格式路由
  - 根据扩展名/MIME 类型选择对应解析器
  ↓
[步骤2] 解析与归一化
  - PDF/图片 → MinerU → Markdown + JSON(bbox)
  - Word      → Mammoth → Markdown
  - Excel     → openpyxl → 结构化 JSON（Markdown 仅作展示）
  - TXT/MD    → 直读校验
  - 网页      → trafilatura 抓取 → Markdown
  ↓
[步骤3] 清洗去噪
  - 去除页眉页脚、水印、重复空行
  - 修正乱码字符
  - 合并被分页切断的段落
  ↓
[步骤4] 结构感知切分
  - 按 Markdown 标题层级（H1/H2/H3）划分语义边界
  - 在层级边界内再按 Chunk 大小切分
  - 保留每个 Chunk 的标题路径（breadcrumb）
  ↓
[步骤5] 向量化
  - 调用选定 Embedding 模型
  - 写入 Milvus
```

**为什么必须先归一化再切分**：

| 直接切纯文本的问题 | 归一化后的改善 |
|---|---|
| 标题与正文被切断，切片失去上下文 | 按 Markdown 标题边界切分，每片自带所属章节 |
| 表格被切成碎片，语义全失 | 表格整体保留或转为结构化 JSON |
| 跨页段落被拦腰截断 | 清洗阶段合并被分页切断的段落 |
| 无法定位原文位置 | JSON(bbox) 保留页码与坐标，支持溯源 |
| 切分策略一刀切 | 可按标题层级做结构感知切分 |

**MinerU 的适用边界与注意事项**：

- ✅ **擅长**：PDF 版面分析、扫描件 OCR、公式识别、复杂表格识别、多栏排版
- ⚠️ **性能**：CPU 环境单页解析需数秒至数十秒，生产环境建议 GPU 部署，并采用**异步任务队列**
- ⚠️ **许可**：MinerU 采用 AGPL-3.0 协议，需法务确认 SaaS 场景下的合规性；建议以独立微服务方式部署，仅做进程间调用，不修改源码
- ⚠️ **Excel 特例**：表格类文件强转 Markdown 会丢失合并单元格和数值类型，检索效果反而下降，因此保留结构化 JSON 入库

##### 2.2.4.2.2 文件处理状态机

**状态定义**（每个文件独立维护一个状态）：

| 状态 | 含义 | 用户可见信息 |
|------|------|-------------|
| `queued` | 排队等待处理 | 「排队中（前面还有 N 个文件）」 |
| `parsing` | 正在解析与归一化 | 「解析中 35%」 |
| `chunking` | 正在切分 | 「切分中」 |
| `embedding` | 正在向量化 | 「向量化中 80%」 |
| `success` | 处理完成 | 「已完成，共 512 个文本块」 |
| `failed` | 处理失败 | 「失败原因：文件加密无法解析」 |

**状态流转**：

```
queued → parsing → chunking → embedding → success
                    ↓           ↓           ↓
                  failed      failed      failed
```

**进度计算规则**：
- `parsing` 阶段：按「已解析页数 / 总页数」计算真实进度（不做动画伪造）
- `chunking` 阶段：通常在数秒内完成，不显示百分比
- `embedding` 阶段：按「已向量化块数 / 总块数」计算进度
- 失败后可重试，重试从 `queued` 重新开始

**失败重试规则**：
- **不限重试次数**，用户可无限次重试
- **所有失败类型均可重试**，不做「可恢复/不可恢复」的区分

   - 图片：直接展示原图
   - Word/Excel：展示原始内容或下载链接
   - 网页：展示原始 URL 与抓取时间

2. **转换后 Markdown**
   - 展示归一化后的 Markdown 文本
   - 保留标题层级高亮，便于人工核对结构是否正确
   - 表格类文件在此标签展示表格 Markdown（仅作肉眼核对）
   - 提供「下载 Markdown」按钮

3. **切片预览**
   - 以卡片列表形式展示每个 Chunk 的内容
   - 每个切片显示：序号、所属标题路径、字符数、内容
   - 点击切片可显示其在原文中的位置（依赖 JSON bbox 坐标）
   - 支持翻页浏览

- 运营人员在上线前发现解析错误（尤其是扫描件、复杂表格）
- 避免脏数据污染向量库
- 为后续「重新索引」提供依据

**分割符配置规则**：

| 能力 | 说明 |
|------|------|
| 内置分隔符 | 空行 `\n\n`、单个换行 `\n`、句号 `。`、问号 `？`、感叹号 `！`、分号 `；` |
| 选择方式 | 复选框多选，可选用一个或多个 |
| 自定义分隔符 | 可添加任意数量的自定义分隔符，如「第X章」「第X条」「【」 |
| 优先级 | 列表顺序即匹配优先级，支持上下调整（↑↓） |
| 删除 | 自定义分隔符可删除；内置分隔符只能取消勾选 |

**切分逻辑**：
```
1. 按标题层级（Markdown H1/H2/H3）划分一级语义边界
2. 在一级边界内，按分隔符优先级依次尝试切分
   - 优先用列表第一位的分隔符
   - 若切出的片段仍超过 Chunk 大小，用下一位分隔符继续切
   - 直到片段小于 Chunk 大小或所有分隔符用尽
3. 按重叠长度在相邻块之间补充上下文
4. 为每个 Chunk 记录所属标题路径（breadcrumb）
```

**Chunk 参数配置**：

| 配置项 | 可选值 | 说明 |
|-------|--------|------|
| Chunk 大小 | 512 字 / 1024 字 / 2048 字 | 每个文本块的字符数 |
| 重叠长度 | 0 / 50 / 100 / 200 字 | 相邻块的重叠部分，避免语义截断 |

**推荐默认值**：Chunk = 1024 字，重叠 = 100 字，分割符 = 空行 + 单个换行。

**配置变更的生效范围（关键规则）**：

配置变更分两类，后果不同，处理方式也不同：

| 变更类型 | 生效范围 | 是否重建 | 是否暂停检索 |
|---------|---------|---------|-------------|
| **切分参数**（Chunk 大小、重叠长度、分割符） | 仅对新上传的文档生效 | 不重建 | 不暂停 |
| **向量化模型** | 影响整个知识库的向量空间 | 需整库重建 | 重建期间暂停检索 |
| **重排序模型** | 立即生效（重排序作用于检索结果，不涉及向量） | 不重建 | 不暂停 |

**为什么切分参数不触发重建**：
- 切分参数往往需要试探性调优（试 512 还是 1024 效果更好）
- 若每调一次就要求整库重建，运营会因成本过高而不敢优化
- 已入库文档的向量仍然有效，只是切片粒度与后续文档不一致
- 系统需在文档列表中明确标注每个文档入库时使用的切分参数，避免运营误以为参数已全局生效

**向量化模型变更流程**（引用 2.2.5.5）：
1. 保存配置时弹窗提示：「更换向量化模型后，该知识库的 N 个文档需重新入库，是否继续？」
2. 确认后知识库标记为「待重建」
3. 待重建期间该知识库暂停参与 RAG 检索
4. 管理员点击「开始重建」手动触发重建流程
5. 重建完成后清除标识，恢复检索

##### 2.2.4.4 向量化模型配置

**可选模型**（B 端用户可选择）：

1. **OpenAI Embedding**
   - 模型：text-embedding-ada-002
   - 向量维度：1536
   - 优点：效果好，多语言支持
   - 缺点：需要 API Key，按量付费
   - 适用：对效果要求高的场景

2. **本地开源模型**
   - 模型：BGE-M3 / BGE-Large-ZH
   - 向量维度：1024
   - 优点：免费，数据不出本地
   - 缺点：需要本地部署，效果略低于 OpenAI
   - 适用：预算有限或数据敏感场景

3. **其他第三方服务**
   - 支持接入其他 Embedding API
   - B 端可配置 API 地址和 Key

**向量数据库**：
- 技术选型：**Milvus**
- 索引类型：HNSW（高性能近似最近邻搜索）
- 相似度度量：余弦相似度（Cosine Similarity）

##### 2.2.4.6 文件更新策略

**场景 1：同名文件上传（更新）**
```
用户上传：《故宫游览指南-v1.0.pdf》
一周后上传：《故宫游览指南-v2.0.pdf》（门票价格更新）

系统处理：
1. 检测到同名文件
2. 自动覆盖旧版本
3. 删除旧向量数据
4. 重新分块和向量化
5. 记录更新日志
```

**场景 2：知识冲突处理**
```
文档 A：故宫门票 60 元（上传于 2023-01）
文档 B：故宫门票 80 元（上传于 2024-01）

用户查询："故宫门票多少钱？"

系统处理：
- RAG 检索到两个文档
- 按上传时间排序，优先返回最新文档
- Agent 回答："根据 2024 年信息，故宫门票 80 元（旺季价格）"
- 来源标注：[来源：故宫游览指南-v2.0.pdf，更新于 2024-01]
```

**场景 3：增量更新**
```
知识库已有 100 个文档
新增 5 个文档

系统处理：
- 只对新增文档进行分块和向量化
- 不影响已有文档的向量数据
- 向量数据库支持增量插入
```

#### 2.2.5 模型管理

**功能定位**：本项目对模型依赖度高，对话 Agent、RAG 知识库、知识图谱解析、重排序等环节均需调用模型。模型管理提供统一的模型注册、分类、启停、默认值配置与调用统计能力，避免各业务模块各自硬编码模型配置。

##### 2.2.5.1 模型分类（固定枚举）

系统预置五类模型，类别决定模型在业务中的用途，**不可由管理员新增类别**：

| 类别 | 标识 | 用途 | 使用方 |
|------|------|------|--------|
| 文本对话 | `chat` | 意图识别、Agent 推理、回答生成 | 智能对话、行程规划 |
| 图片理解 | `vision` | 图片内容识别、景点图片描述 | 知识库图片解析、景点详情 |
| 向量化 | `embedding` | 文档切片向量化、查询向量化 | RAG 知识库 |
| 重排序 | `rerank` | 检索结果精排 | RAG 知识库 |
| OCR 解析 | `ocr` | 扫描件文字识别 | 文档归一化链路 |

**约束**：
- 每个类别下可以有多个模型，但**平台默认为每类只设一个默认值**
- 不同类别的模型不可互换使用（如不能把向量化模型用作对话）

##### 2.2.5.2 模型注册

**注册方式**：统一采用 OpenAI 兼容接口封装（LiteLLM 风格），不为每家厂商单独适配。只要目标服务提供 OpenAI 兼容的 `/v1/chat/completions`、`/v1/embeddings` 等接口即可接入。

**字段清单**：

| 字段 | 必填 | 可修改 | 说明 |
|------|------|--------|------|
| 模型名称 | ✅ | ✅ | 展示名，如「DeepSeek-V3」「BGE-M3」 |
| 模型类别 | ✅ | ❌ | 五类之一，注册后不可变更 |
| 调用模型 ID | ✅ | ✅ | 接口实际使用的 model 参数，如 `deepseek-chat`、`bge-m3` |
| 接口地址 Base URL | ✅ | ✅ | OpenAI 兼容端点根地址 |
| API Key | 条件必填 | ✅ | 本地部署模型可能无需鉴权，此时可留空 |
| 最大上下文长度 | 文本类必填 | ✅ | 单位 token，用于上下文压缩阈值计算 |
| 单次最大输出 | 文本类 | ✅ | 单位 token |
| 时间单位 | - | - | - |
| 超时时间 | ❌ | ✅ | 默认 60s |
| 并发上限 | ❌ | ✅ | 防止单模型被打爆 |
| 单价（输入/输出） | ❌ | ✅ | 用于成本估算，文本类按 token 计价，向量化类按 token 或条数计价 |
| 模型描述 | ❌ | ✅ | 备注用途、能力特点 |
| 启用状态 | ✅ | ✅ | 启用 / 禁用 |
| 是否为该类别默认 | ❌ | ✅ | 每个类别最多一个默认 |

**重要设计：向量维度不在注册字段中**

向量维度作为**配置文件项**（后端代码读取并传递给向量化调用），不在页面上暴露、不进入模型注册字段。原因：
- 维度是调用参数而非模型固有属性，暴露给运营容易误改
- 一旦页面可改，会导致已建 Milvus Collection 维度不匹配，全库向量失效
- 配置文件修改属于有意识的运维操作，会自然触发「重新入库」流程

**注册后不可修改项**：
- 模型类别（改了会导致业务调用错乱）

##### 2.2.5.3 模型状态与操作

**状态定义**：

| 状态 | 含义 | 可被业务模块选用 |
|------|------|-----------------|
| 启用 | 正常可用 | ✅ |
| 禁用 | 保留配置但不参与调用 | ❌ |

**支持的操作**：

| 操作 | 说明 | 约束 |
|------|------|------|
| 注册 | 新增模型 | 同一类别下调用模型 ID + Base URL 不可重复 |
| 编辑 | 修改可修改字段 | 模型类别不可改 |
| 启用 / 禁用 | 切换可用状态 | 禁用前需确认该模型是否被引用 |
| 设为默认 | 设为该类别默认模型 | 同类别原默认自动取消 |
| 删除 | 物理删除 | **有知识库/业务配置引用时禁止删除** |
| 连通性测试 | 发送测试请求验证可用性 | 见 2.2.5.6 |

**删除保护规则**：

```
删除模型前校验引用关系：
  - 被知识库的向量化模型配置引用 → 禁止删除
  - 被知识库的重排序模型配置引用 → 禁止删除
  - 是某类别的当前默认模型 → 禁止删除（需先改默认）
  - 无任何引用 → 允许删除
```

**提示文案示例**：
> 「该模型正被 3 个知识库使用，无法删除。请先在这些知识库中更换模型后再试。」

##### 2.2.5.4 默认模型策略

**三级生效规则**：

```
1. 平台级默认（每类一个）
   ↓ 新建知识库时继承
2. 知识库级配置（仅向量化模型、重排序模型可配置）
   ↓ 运行时优先
3. 用户会话级切换（仅文本对话类）
```

**知识库级配置规则**：
- 知识库创建时，向量化模型自动继承平台默认值
- 可展开修改，**候选范围仅限于「该类别下已启用」的模型**
  - 若该类别只注册了 1 个模型 → 无可选余地，固定为该模型
  - 若注册了多个 → 可在启用的模型中选择
- 已禁用的模型不出现在候选列表中

**新建知识库交互**：

```
┌──────────────────────────────────────┐
│  创建知识库                           │
├──────────────────────────────────────┤
│  名称：[________________]             │
│  描述：[________________]             │
│                                      │
│  ▸ 高级配置（点击展开）               │
│    向量化模型：[BGE-M3（默认）▼]      │
│    重排序模型：[无 ▼]                 │
└──────────────────────────────────────┘
```

默认折叠，展开后可选。符合「大多数场景用默认，需要时可调整」的使用模式。

##### 2.2.5.5 知识库配置变更的约束

知识库配置变更分为两类，后果不同，处理方式也不同。

**变更类型对比**：

| 变更类型 | 影响范围 | 是否重建 | 是否暂停检索 |
|---------|---------|---------|-------------|
| **切分参数**（Chunk 大小、重叠长度、分割符） | 仅对后续新上传的文档生效 | 不重建 | 不暂停 |
| **向量化模型** | 影响整个知识库的向量空间 | 需整库重建 | 重建期间暂停检索 |
| **重排序模型** | 立即生效（重排序作用于检索结果，不涉及向量） | 不重建 | 不暂停 |

**为什么两类变更区别对待**：

- **切分参数**：已入库文档的向量仍然有效，只是切片粒度与后续文档不一致，不影响向量的可比较性。且切分参数往往需要试探性调优（试 512 还是 1024），若每次调整都强制重建，运营会因成本过高而不敢优化。
- **向量化模型**：不同模型产生的向量处于不同的语义空间，**距离不可比较**，混存会导致检索静默失效（不报错但结果完全不可信）。因此必须整库重建。

**切分参数变更的可见性保障**：

虽然不重建，但必须让运营清楚知道哪些文档使用的是旧参数，避免误以为参数已全局生效：
- 文档列表新增「入库切分参数」列，显示该文档实际入库时的 Chunk / 重叠值
- 与知识库当前参数不一致时，标注 ⚠️ 与「（旧参数）」
- 提供「重建」按钮，供运营在确认新参数更优后手动将该文档按新参数重新解析

**向量化模型变更流程**：

```
管理员在知识库配置中更换向量化模型
  ↓
弹窗确认：「更换向量化模型后，该知识库的 85 个文档需重新入库。
          是否继续？」
  ↓
[取消] → 不生效
[确认] → 配置生效，知识库标记为「待重建」
```

**待重建状态**：

| 项 | 行为 |
|---|---|
| 知识库在列表中的标识 | 显示红色徽标「待重建」 |
| 该知识库是否参与 RAG 检索 | **暂停检索**，检索时返回「该知识库正在重建，暂不可用」 |
| 重建触发方式 | 管理员点击「开始重建」按钮手动触发 |
| 重建过程 | 复用文档处理状态机（queued → parsing → chunking → embedding） |
| 重建完成后 | 清除「待重建」标识，恢复检索 |

**设计理由**：模型不匹配时检索结果的语义距离不可信。暂停检索可以让问题显性化，避免用户误判为「RAG 效果差」。

##### 2.2.5.6 连通性测试

**测试方式**：向模型接口发送一个最小化的真实请求，验证可用性。

| 类别 | 测试请求 | 成功判定 |
|------|---------|---------|
| 文本对话 | 发送「你好」，max_tokens=5 | 返回 200 且有内容 |
| 图片理解 | 发送一张内置测试图 + 简单问句 | 返回 200 且有内容 |
| 向量化 | 对「测试」二字向量化 | 返回 200 且向量维度与配置文件一致 |
| 重排序 | 传入 query + 2 个文档 | 返回 200 且含分数 |
| OCR 解析 | 发送一张内置测试图 | 返回 200 且有文字 |

**测试结果展示**：

```
┌────────────────────────────────────┐
│  🔗 连通性测试 - DeepSeek-V3        │
├────────────────────────────────────┤
│  ✅ 接口连通        耗时 320ms      │
│  ✅ 鉴权通过                        │
│  ✅ 响应格式正确                    │
│  ✅ 模型可用        首字延迟 180ms  │
├────────────────────────────────────┤
│  状态：测试通过                     │
└────────────────────────────────────┘
```

**失败时的分层提示**（区分故障原因，便于排查）：

| 失败类型 | 提示 |
|---------|------|
| 网络不通 / 超时 | 「无法连接到接口地址，请检查 Base URL 与网络」 |
| 401 / 403 | 「鉴权失败，请检查 API Key」 |
| 404 | 「接口路径不存在，请确认是否为 OpenAI 兼容端点」 |
| 429 | 「请求过于频繁，已被限流」 |
| 5xx | 「模型服务端异常」 |
| 响应格式不符 | 「返回格式不符合 OpenAI 规范，请确认接口兼容性」 |
| 向量维度不一致 | 「返回向量维度与配置文件不一致（期望 1024，实际 768）」 |

##### 2.2.5.7 模型不可用时的用户行为

**模型调用失败的重试规则**

模型调用失败时，**先自动重试，仍失败则不降级，由用户显式切换**：

| 阶段 | 行为 |
|------|------|
| 第 1 次调用 | 失败 |
| 自动重试 | 最多重试 2 次 |
| 重试后仍失败 | 返回明确错误 + 可用模型列表，由用户手动选择 |

**为什么先重试而不直接报错**：超时、网络抖动、服务端偶发 5xx 属于瞬时故障，重试往往能恢复，直接报错会让用户体验变差。

**为什么重试后仍不自动降级**：
- 不同模型能力差异大，静默切换会导致同一次对话质量突变难以排查
- 用户对「我正在用什么模型」应有知情权和选择权

**完整交互流程**：

```
用户发起对话
  ↓
调用该类别默认模型
  ↓
├─ 成功 → 正常返回
└─ 失败 → 自动重试（最多 2 次）
          ├─ 重试成功 → 正常返回
          └─ 重试仍失败 → 返回明确错误 + 可用模型列表
                          「模型 A 暂时不可用（原因：请求超时）。
                           您可以切换到以下模型继续：
                           [模型 B] [模型 C]」
```

**对话界面的模型选择入口**：

```
┌─────────────────────────────────┐
│  🤖 智能助手          [DeepSeek-V3 ▼] │
└─────────────────────────────────┘
                            ↑ 点击可切换
```

**切换生效范围**：
- **仅当前会话内生效**
- 开启新会话时恢复为平台默认模型
- 不写入用户长期偏好（避免用户忘记曾改过配置，后续效果异常时排查困难）

##### 2.2.5.8 用户调用额度限制

**约束对象：用户，非平台**

平台本身对模型调用不设总量限制，模型也没有单独额度。限制只发生在**用户维度**：

```
用户 A 用完自己的额度 → A 无法继续调用
                      → 不影响用户 B
                      → 平台与模型本身不受影响
```

**为什么采用用户级而非平台级额度池**：
若做成平台共享池，某个重型用户调用昂贵模型烧穿额度后，会导致所有用户（包括只想用免费本地模型的用户）一起被拒绝，成本管控反而失效。

**额度计量：次数 + token 双限**

两项任一超限即拒绝：

| 维度 | 示例 | 作用 |
|------|------|------|
| 调用次数 | 每日 100 次 | 防高频滥用，用户易理解 |
| Token 总量 | 每日 10 万 token | 反映真实成本，防超长 prompt 单次烧穿 |

**额度覆盖范围**

| 调用来源 | 是否计入用户额度 | 说明 |
|---------|----------------|------|
| C 端对话（Agent 推理、检索、生成） | ✅ 计入 | 消耗用户自己的额度 |
| B 端文档处理（向量化、OCR、重排序） | ❌ 不计入 | 属系统运维行为，不消耗任何用户额度 |

**B 端文档处理的调用记录**：
- 不计入用户额度，但**计入模型调用统计**（按模型归集次数与 token）
- 便于运营核算知识库建设成本

**用户可见展示**（个人中心）：

```
┌────────────────────────────────────┐
│  今日模型调用额度                   │
│  ├ 调用次数：32 / 100               │
│  └ Token：  28,450 / 100,000        │
└────────────────────────────────────┘
```

展示位置：**仅个人中心**，作为独立区块。对话界面不重复展示。

**额度不足预警**：剩余额度低于 10% 时，**个人中心与对话界面双处提示**

| 位置 | 提示形式 |
|------|---------|
| 个人中心 | 额度区块显示黄色警示色 +「额度即将用尽」 |
| 对话界面 | 对话页顶部或输入区附近显示轻量提示条 |

**重置周期：自然日**
- 每日 00:00（服务器时区）清零
- 与用户直觉一致（「今天还剩几次」）

**超限行为：直接报错**

```
「您的今日调用额度已用尽（100 次 / 10 万 token）。
 额度将于明日 00:00 重置。」
```

**额度配置入口**：B 端系统设置 → 用户额度配置

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| 每日调用次数上限 | 100 | 全平台统一 |
| 每日 token 上限 | 100,000 | 全平台统一 |

**预留能力**（当前统一额度，后续可扩展）：
- 支持对单个用户单独调整额度
- 支持按用户等级差异化额度

##### 2.2.5.9 调用统计与监控

**统计维度**：

| 指标 | 说明 |
|------|------|
| 调用次数 | 按模型 / 按天 |
| Token 用量 | 输入 token + 输出 token |
| 平均响应延迟 | 用于发现慢模型 |

#### 2.2.6 系统管理

**角色划分**：当前仅启用两种角色

| 角色 | 说明 | 权限 |
|------|------|------|
| **超级管理员** | 可登录 B 端 | 拥有全部权限 |
| **普通用户** | C 端用户 | 无法登录 B 端 |

**设计原则：权限模型按数据建模，不硬编码在代码中**

虽然当前只有两种角色，但权限体系按**数据驱动**方式设计：

- 权限项按「模块 × 操作」细粒度建模，可单独控制增、删、改、查
  - 如「景点管理 - 删除」「用户管理 - 封禁」为独立权限项
- 角色与权限的对应关系存储在数据表中，而非代码逻辑中
- 当前只配置了「超级管理员 = 全部权限」「普通用户 = 无 B 端权限」两条数据

**这样设计的目的**：后续新增角色（如内容运营、数据分析）时，**只需在后台配置角色与权限的对应关系，无需修改代码**。

**系统用户管理**
- B 端管理员账号管理（新建、编辑、禁用、重置密码）
- 为账号分配角色

**操作日志**
- **记录范围**：所有增、删、改操作
- 不记录查询操作
- 记录内容：操作人、操作时间、操作模块、操作类型、操作对象、操作结果

#### 2.2.7 数据看板

**刷新频率**：分层刷新

| 数据类型 | 刷新频率 |
|---------|---------|
| 核心指标（如注册用户数、计划总数） | 实时 |
| 趋势图（如新增用户趋势、DAU 曲线） | 每日凌晨更新 |

**用户指标**
- 注册用户数、活跃用户数（DAU/MAU）
- 新增用户趋势（日/周/月）

**内容指标**
- 景点/餐厅/酒店总数
- 各分类占比（历史人文/自然景色等）
- 热门景点排行：**按最终热度值排序**（基础权重 × 系数 + 用户行为得分 × 系数），与首页热度排行口径一致

**业务指标**
- 创建计划数、完成计划数
- **计划完成率 = 已完成计划数 ÷（已完成 + 进行中 + 待进行）**
  - 分母排除「规划中」的计划，避免长期未确认的计划拉低完成率
- 平均计划天数、平均预算区间
- 热门目的地城市排行

**交互指标**
- 聊天会话数、平均对话轮次
- 用户提问热门话题分类

**UGC 指标**
- 足迹总数、足迹照片数、游记数
- 景点评分分布

**推荐效果指标**
- 推荐点击率（CTR）
- 热度算法效果评估

## 3. 业务流程

### 3.1 旅游计划生成流程

```
1. 用户在聊天窗口输入需求
   "我想5月1日-5月3日去北京，预算3000元，喜欢历史文化"

2. LLM 解析用户意图，提取参数：
   - 目的地：北京
   - 日期：2024-05-01 至 2024-05-03（3天）
   - 预算：3000元
   - 偏好：历史文化

3. 系统执行生成流程：
   
   a. RAG 检索景点
      - 向量搜索：查询北京+历史文化类景点
      - 过滤条件：开放时间、门票价格符合预算
      
   b. MCP 工具查询交通
      - 查询用户所在城市 → 北京的交通方式和价格
      
   c. 地理优化
      - 获取候选景点的地理坐标
      - 调用地图 API 计算距离矩阵
      - 路径优化算法：按地理位置聚类，同一天安排相近景点
      
   d. LLM 生成完整行程
      - 输入：景点列表、交通信息、预算约束、时间约束
      - 输出：结构化 JSON（每日详细行程）
      
   e. 补充餐厅和酒店
      - 基于景点位置，查询附近餐厅（符合预算）
      - 推荐酒店（考虑地理位置和价格）

4. 返回生成的计划给用户
   - 展示每日行程
   - 显示预算明细
   - 用户可编辑调整

5. 用户确认后，计划状态 → "待进行"
```

### 3.2 热度计算流程

```
1. 用户行为实时埋点
   - 浏览景点详情页 → view_count +1
   - 点击景点 → click_count +1
   - 收藏景点 → favorite_count +1
   - 将景点加入计划 → plan_count +1
   - 评分 → 更新 avg_rating

2. 定时任务（每小时执行）
   a. 汇总用户行为数据
      behavior_score = (view_count × 1 + click_count × 2 + 
                        favorite_count × 5 + plan_count × 10 + 
                        avg_rating × 20) / 100
   
   b. 归一化处理（0-100分）
   
   c. 计算最终热度
      final_popularity = base_popularity × 0.6 + behavior_score × 0.4
   
   d. 更新 popularity_stats 表

3. 首页排行榜读取 final_popularity，按降序展示
```

### 3.3 用户偏好提取流程

```
1. 触发时机
   - 用户完成一次旅游计划（计划状态 → 已完成）
   - 用户添加足迹
   - 定期（如每周）批量分析活跃用户

2. 数据收集
   - 对话历史：提取关键词和意图
   - 足迹记录：分析去过的景点类型
   - 旅游计划：偏好的景点、预算范围、旅行天数
   - 评分数据：高分景点的共性

3. LLM 分析
   - 输入：用户的所有行为数据摘要
   - 输出：结构化用户画像 JSON
   ```json
   {
     "景点类型偏好": {"历史人文": 0.7, "自然景色": 0.3},
     "预算敏感度": "中",
     "旅行同伴": "家庭",
     "平均旅行天数": 4,
     "偏好季节": ["春季", "秋季"],
     "地域偏好": ["华北", "江南"]
   }
   ```

4. 更新 user_profiles 表

5. 应用场景
   - 新会话时，LLM 加载用户画像，提供个性化建议
   - 推荐系统基于画像推荐相关景点
```

## 4. 非功能性需求

### 4.1 性能要求
- **对话响应时间**：流式输出，首字延迟 < 2 秒
- **景点列表加载**：< 1 秒
- **旅游计划生成**：< 30 秒（含 LLM 调用、地图 API 调用、路径优化）
- **热度排行更新**：准实时，延迟 < 1 小时
- **并发支持**：初期支持 1000 DAU，后期可扩展至 10 万 DAU

### 4.2 安全性要求
- **数据加密**：用户密码哈希存储（bcrypt），敏感数据传输 HTTPS
- **身份认证**：JWT Token 机制，过期时间 7 天
- **权限控制**：B 端基于角色的访问控制（RBAC）
- **防刷机制**：
  - 短信验证码：同一手机号 1 分钟/次，每日 5 次上限
  - 对话频率限制：单用户 10 次/分钟
  - API 调用：IP 限流

### 4.3 可用性要求
- **系统可用性**：99.5%（初期），99.9%（稳定期）
- **数据备份**：每日全量备份，实时增量备份
- **容灾恢复**：RTO（恢复时间目标）< 4 小时，RPO（恢复点目标）< 1 小时

### 4.4 可扩展性
- **微服务架构**：核心模块独立部署（用户服务、对话服务、计划服务、推荐服务）
- **数据库分库分表**：用户表、行为表按用户 ID 分片
- **缓存策略**：
  - 景点详情：Redis 缓存，TTL 1 小时
  - 热度排行：Redis 缓存，TTL 1 小时
  - 用户画像：Redis 缓存，TTL 1 天

### 4.5 兼容性
- **浏览器支持**：Chrome 90+、Firefox 88+、Safari 14+、Edge 90+
- **移动端**：响应式设计，支持 iOS 12+ 和 Android 8+
- **未来扩展**：预留移动端原生 APP 接口

## 5. 风险与挑战

### 5.1 技术风险
- **LLM 成本控制**：对话频繁可能导致 API 调用成本高昂
  - 缓解：设置用户免费额度，超出后限流或收费
- **地理优化算法复杂度**：TSP 问题计算量大
  - 缓解：限制单日景点数量（如最多 5 个），使用启发式算法
- **RAG 准确性**：检索结果可能不精准
  - 缓解：持续优化向量模型，增加人工审核

### 5.2 业务风险
- **数据冷启动**：初期景点、餐厅、酒店数据不足
  - 缓解：先聚焦 10-20 个热门城市，批量导入数据
- **用户留存**：旅游是低频需求，用户粘性可能不高
  - 缓解：增加足迹、社交等高频功能，定期推送旅游灵感

### 5.3 合规风险
- **用户隐私**：对话历史涉及个人偏好
  - 缓解：明确隐私政策，提供数据导出和删除功能
- **地图服务合规**：需遵守测绘法规
  - 缓解：使用有资质的地图服务商
