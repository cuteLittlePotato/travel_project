#### [M17-T02] 热度计算算法（纯函数）

- 所属模块：M17 推荐引擎
- 优先级：P0
- 依赖：无
- 关联文档：需求 §3.2（热度计算流程）、数据库设计 §3.2（popularity_stat）
- 任务类型：后端

- 任务描述：实现热度计算的**纯算法函数**（无 IO、无 DB 访问、无定时任务）。输入原始行为计数，输出 `behavior_score` 与 `final_popularity`。

- 交付物：
  - [x] `backend/app/modules/recommend/popularity_algorithm.py`
  - [x] `backend/app/modules/recommend/constants.py` — 权重常量
  - [x] `backend/tests/unit/test_popularity_algorithm.py` — 32 项
  - [x] 归一化策略（min-max）
  - [x] 权重计算函数

- 验收标准（DoD）：
  - [x] `behavior_score` 归一化到 0-100（单测）
  - [x] `final_popularity = base × 0.6 + behavior × 0.4`（单测）
  - [x] 无行为数据时 `behavior_score=0`（单测）
  - [x] **函数为纯函数：不访问 DB/Redis/外部服务**（AST 检查导入 + 子进程导入陷阱）
  - [x] 模块导入不触发任何 IO（导入测试）

- 边界与异常：全集最大值与最小值相同时的除零保护。

- **实现说明（2026-11-08）**：
  1. **权重不含收藏**：需求 §3.2 的公式含 `favorite_count × 5`，但评审 Q9 已
     删除收藏功能及 `popularity_stat.favorite_count` 字段。保留该权重会让
     字段缺失时恒为 0，读代码的人误以为漏实现，因此直接去掉。
     实际参与计算的四项：浏览 ×1、点击 ×2、加入计划 ×10、平均分 ×20。
  2. **评分先换算量纲**：`avg_rating` 是 0-5 分制，×20 后落到 0-100，
     否则 0-5 的数值会被浏览/点击量淹没。
  3. **零行为景点必须参与 min-max**：初版实现先把零行为景点过滤掉再归一化，
     导致「1 个活跃 + 9 个零行为」退化成单元素集合、触发除零保护，
     活跃景点反得 0 分。零行为景点是合集的最小值，剔除是错误的。
     已改为全量参与，测试锁定此行为。
  4. **除零时给 0 不给 100**：全集分值相同时统一 0 分。
     给 100 会让「全站无人访问」被误判为「全站最热」。
  5. **Decimal 全程计算**：入参用 `Decimal(str(x))` 转换，避免 float
     的二进制误差累积到 `NUMERIC(10,2)` 的落库值上。
  6. **分层接口**：`calculate_raw_score`（单个）/ `calculate_raw_scores`（批量）/
     `normalize_scores`（归一化）/ `calculate_behavior_scores`（一步到位）/
     `score_attractions`（返回行为分 + 最终热度二元组）。数据管道可按需选用。
  7. **纯函数验证方式**：DoD 原文要求 grep 无 `session|redis|await.*client`，
     但注释里说明「不访问缓存」也会命中文档字符串。改为**剥掉注释/docstring
     后对 AST 标识符断言**，并增加子进程导入陷阱测试（导入时若碰到
     `sqlalchemy`/`redis`/`asyncpg`/`httpx` 即失败）。

- **与其他任务的关系（职责边界）**：
  - 本任务：**只做算法**，输入是已聚合的行为计数（dict），输出是分值（float）
  - `M11-T10`：**数据管道**，负责读取 `user_event`、调用本任务的算法、写入 `popularity_stat`、定时调度
  - 两者**无代码依赖**，M11-T10 通过函数调用或 HTTP 内部接口使用本任务

- 预估工时：1h（实际约 1.5h）
- 状态：DONE
