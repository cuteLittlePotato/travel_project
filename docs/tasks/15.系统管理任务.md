- 交付物：

  - [x] `admin_user.token_version` 存在且默认 0（DB 断言）
  - [x] `role_permission` 唯一约束 `(role_id, permission_id)`
  - [x] `admin_user_role` 唯一约束 `(admin_user_id, role_id)`
  - [x] `permission.action` CHECK 含 `create/read/update/delete/export/manage`
  - [x] 规范检查：无物理外键；`site_setting.setting_key` 唯一

- 边界与异常：`admin_user` 与 `user` 完全分离（评审 §Q10）。

- **实现说明（2026-11-08）**：
  1. **迁移无需新写**：M0-T13 已生成 `0013_m15_system.py`（含七张表、
     全部索引、CHECK 约束、updated_at 触发器）。本任务只补 ORM。
  2. **一次通过 drift 检查**：七张表的基类选择按「有无 created_at /
     updated_at」严格对应——
     - `admin_user` / `role`：两列都有 → `BaseModel`
     - `permission` / `role_permission` / `admin_user_role` /
       `operation_log`：只有 created_at
     - `site_setting`：只有 updated_at
  3. **`operation_log` 没有 read 动作**：DDL 注释写明「仅记录增删改
     与登录登出，不记录查询」。查询量大会淹没真正需要审计的写操作。
     测试用 `assert "read" not in check_sql` 锁定这一取舍。
  4. **C 端用户表没有密码列**：写测试时我先假设 `user` 表有
     `password_hash`，跑出来才发现没有——M01 的 C 端登录只走验证码与
     OAuth，设计上就没有密码。这是有意的：去掉密码列等于从设计上
     消除弱口令这个攻击面。已把「C 端无密码、B 端有密码」写成断言，
     防止有人「顺手」给用户表加密码。
  5. **`ip_address` 列宽 45**：IPv6 最长 45 字符，有测试断言，
     防止有人按 IPv4 的 15 字符改建表。
  6. **`site_setting.setting_value` 是 JSONB**：配置值可能是字符串、
     数字、数组或对象，JSONB 让它们统一存储且可查询。

#### [M15-T02] 初始化数据（角色与权限项）

- 所属模块：M15 系统管理
- 优先级：P0
- 依赖：M15-T01
- 关联文档：评审 §Q13（权限数据驱动）、需求 §2.2.6
- 任务类型：DB迁移

- 任务描述：编写数据迁移，初始化两个角色（超级管理员 / 普通用户）与全部权限项（按「模块 × 操作」细粒度）。

- 交付物：
  - [x] `backend/app/db/migrations/versions/0015_m15_seed_permissions.py`
  - [x] `backend/app/modules/system/permissions.py` — 权限项清单（单一事实源）
  - [x] `backend/tests/unit/test_system_seed.py` — 28 项
  - [x] 权限项清单（8 个 B 端模块，76 条）

- 验收标准（DoD）：
  - [x] 初始化后 `role` 表有 2 条记录（DB 断言）
  - [x] 权限项数量与模块数匹配（每模块至少 4 个 CRUD 权限）（DB 断言）
  - [x] 超级管理员角色拥有全部权限（`role_permission` 记录数 = 权限总数）（DB 断言）
  - [x] 规范检查：数据迁移可重复执行（幂等，`ON CONFLICT DO NOTHING`）
  - [x] **规范检查：无物理外键**

- 边界与异常：后续新增权限项时的增量迁移策略。

- **实现说明（2026-11-08）**：
  1. **权限项清单是单一事实源**：定义在
     `app/modules/system/permissions.py`，迁移从那里 import，
     不在迁移文件里重复列一份。后续加接口只改这一处 + 生成新迁移。
  2. **实际是 8 个模块，不是 17 个**：任务卡写「覆盖 17 个模块」，
     但 B 端管理接口只涉及 8 个模块（catalog / knowledge_base /
     knowledge_graph / model / quota / user_ops / system / dashboard）。
     其余模块没有 B 端管理界面，不需要权限项。共 76 条。
  3. **编码三段式** `module.resource.action`：二分（module.action）
     会把「景点」和「餐厅」的删除权限绑在一起，运营可能只需要管景点。
     三段式让授权精确到单个资源类型。
  4. **动作必须是六种之一**：数据库 `permission.action` 有 CHECK 约束
     （create/read/update/delete/export/manage）。初版写了
     `document.upload` 与 `attraction.import`，两者都非法。
     修正为：
     - `upload` → `create`（上传即创建文档）
     - `import` → **直接删除该权限**，合并进「创建景点」——
       导入本质是批量创建，能建单个景点就该能导入；
       批量带来的风险由接口层的文件大小与行数上限控制。
  5. **固定 UUID 而非随机生成**：
     - 角色 ID 写死（`...0001` / `...0002`），因为代码里按 code 引用，
       每次重跑换 ID 会让权限关联对不上。
     - 权限 ID 用 `uuid5(namespace, code)` **确定性推导**，
       同一个 code 在任何环境得到同一个 ID，便于跨环境排查与增量迁移。
  6. **超级管理员授权用 `SELECT` 而非按清单推导**：这样后续增量迁移
     新增的权限项也会自动包含进来，不必回头改本迁移。
  7. **降级会删数据**：`downgrade` 清理种子角色与全部权限项。
     若线上已基于这些角色配置了管理员，降级会连带删除关联——
     数据迁移降级的固有风险，生产环境不建议降级。
  8. **幂等测试真的执行 SQL**：初版尝试复用迁移函数，但迁移接收的是
     Alembic 的同步 Connection，而测试环境只有 asyncpg，实际上
     根本没执行（被 RuntimeWarning 掩盖）。已改为按同一套
     `INSERT ... ON CONFLICT DO NOTHING` 在库里重放一遍再比对行数。

- 预估工时：1.5h（实际约 2.5h）
- 状态：DONE

#### [M15-T03] 管理员 CRUD 接口

- 所属模块：M15 系统管理
- 优先级：P0
- 依赖：M15-T01, M0-T05
- 关联文档：API §14.1 ~ §14.5
- 任务类型：API

- 任务描述：实现管理员的列表、创建、更新、重置密码、删除。

- 交付物：
  - [x] `backend/app/api/v1/b_end/system.py` — 6 个路由
  - [x] `backend/app/modules/system/service.py`
  - [x] `backend/app/modules/system/repository.py` — 7 个 Repository
  - [x] `backend/app/modules/system/schemas.py`
  - [x] `backend/tests/unit/test_admin_crud_api.py` — 27 项

- 验收标准（DoD）：
  - [x] 用户名重复返回 `25002`（409）（接口测试）
  - [x] 删除仅存的超级管理员返回 `25003`（409）（接口测试）
  - [x] 不能删除自己返回 `25004`（400）（接口测试）
  - [x] 规范检查：响应不含 `password_hash`、`token_version`

- 边界与异常：重置密码后需使目标管理员 Token 失效。

- **实现说明（2026-11-08）**：
  1. **错误码按文档校正**：初版我自定义的 25002~25005 与 API 文档
     冲突。文档定义是 25002=用户名重复、25003=仅存超管、25004=不能删自己、
     25007=原密码错误、25008=新旧密码相同。已全部改正，
     文档未定义的场景占用 25009 及之后（管理员不存在、角色不存在等）。
  2. **密码用 bcrypt**：复用 `app.core.security.hash_password`，
     与 C 端（M01，虽然 C 端无密码）和 M0-T05 同一套实现。
     测试断言库里存的是 `$2` 开头的哈希。
  3. **敏感字段由 schema 保证**：`AdminResponse` 根本不定义
     `password_hash` 与 `token_version`，序列化时自然带不出来，
     不靠每个调用点记得删字段。
  4. **重置密码必须使 Token 失效**：`reset_password` 里
     `increment_token_version`。密码是账号最后一道防线，改了密码
     就应假设旧凭据已泄露。有测试断言 version +1。
  5. **禁用自己也被拒绝**（25006）：虽不在 T03 的 DoD 里，但禁用
     自己与删除自己是同一类不可逆误操作，一并挡住。
  6. **删除保护顺序：先查「删自己」再查「最后一个超管」**。
     删自己是纯操作失误，用户最容易犯，先报这个更符合直觉。
  7. **PATCH 用 `model_fields_set` 判断字段是否传入**：
     `real_name=None`（显式传 null）与「没传」是两种语义，
     用 `model_dump(exclude_unset=True)` 等价但字段判断更直观。
  8. **角色变更是整体替换**：`replace_roles` 先删后插，
     比逐条比对简单且不会漏删。
  9. **「仅存超管」测试需构造场景**：若库里已有超管则 skip，
     避免测试之间互相干扰。

- 预估工时：2h（实际约 2.5h）

- 验收标准（DoD）：

  - [x] 内置角色不可删除，返回 `25006`（400）（接口测试）

- 边界与异常：角色 `code` 唯一性校验。

- **实现说明（2026-11-08）**：
  1. **错误码再次按文档校正**：任务卡 T04 明确 25005=已分配、
     25006=内置角色，与我上一轮自定义的「25005=角色不存在、
     25006=不能禁用自己」冲突。已改为：
     - 25005 = 角色已分配（409）
     - 25006 = 内置角色不可删（400）
     - 角色不存在顺延到 25010，不能禁用自己顺延到 25011
     并同步修正了 T03 测试里的两处断言。
  2. **业务逻辑拆到 `role_service.py`**：`service.py` 已有 300 行，
     角色部分再加进去会过长。按「管理员」与「角色权限」两个关注点拆分。
  3. **权限项同时返回两种形态**：
     - `items`：扁平列表，适合查单个权限、做下拉
     - `groups`：按 module 分组、组内按 action 排序，
       前端渲染勾选树时不必自己分组
     两个形态的总数必须一致，有测试断言。
  4. **删除保护顺序：先判内置，再判已分配**。内置角色是请求本身
     不合法（与当前有没有人用无关），先报这个更准确。
     有测试用 normal 角色锁定该顺序。
  5. **`code` 与 `is_builtin` 不可通过接口修改**：
     - `code` 被代码直接引用（`ROLE_SUPER_ADMIN`）
     - `is_builtin` 由系统判定，能设置就失去了「内置」的意义
     两者都不在 `RoleUpdate` 的字段里，传了会被 Pydantic 忽略。
     有测试断言传了也改不动。
  6. **设置权限是整体替换**：前端提交的是一棵勾选树，用户看到的
     就是「这个角色有哪些权限」，提交的应是完整状态而非差异。
  7. **列表带 `admin_count` 与 `permission_count`**：批量查询，
     避免 N+1。前端可直接据此提示「该角色已分配给 3 个管理员」。

#### [M15-T05] 权限校验中间件

- 所属模块：M15 系统管理
- 优先级：P0
- 依赖：M15-T04, M0-T05
- 关联文档：API §16.3（权限校验矩阵）、评审 §Q13
- 任务类型：后端

- 任务描述：实现基于「模块 × 操作」的权限校验依赖，B 端接口按需声明所需权限项。

- 交付物：
  - [x] `backend/app/api/middleware/permission.py` — `require_permission(code)` 依赖工厂
  - [x] 权限查询（带 Redis 缓存 + 空集合缓存）
  - [x] 三个 B 端路由文件全部接入权限声明（catalog 33 + models 8 + system 15 = 56 处）
  - [x] `backend/tests/unit/test_permission_middleware.py` — 27 项

- 验收标准（DoD）：
  - [x] 无权限访问返回 403 + `25001`（接口测试）
  - [x] 超级管理员绕过权限检查（单测）
  - [x] 权限查询有缓存，缓存失效后重新加载（单测）
  - [x] 规范检查：权限校验**数据驱动**，不硬编码角色判断

- 边界与异常：权限变更后缓存失效策略。

- **实现说明（2026-11-08）**：
  1. **超管不用通配符**：最初设计是让 `super_admin` 持有一条 `*`
     权限项，校验时命中即放行。但这会引入一条不合规的权限记录
     （编码不是 `module.resource.action` 格式），且「超管有哪些权限」
     又变成代码里的隐式规则。
     **最终方案**：种子数据已把全部权限项授予超管，校验时天然通过。
     零特判、零通配符，完全数据驱动。
  2. **空权限集合也要缓存**：Redis 的空 Set 不存在，无法区分
     「没缓存」与「缓存了空集合」。若不处理，没分配角色的管理员
     每个请求都会回源查库。用占位成员 `__empty__` 表示空集合，
     读取时剔除。
  3. **Redis 不可用降级直查库**：权限校验是安全边界，宁可慢也不能
     因为缓存故障就放行或全部拒绝。写缓存失败不影响本次校验结果。
  4. **缓存失效的四个触发点**：
     - 管理员角色变更（`update_admin`）
     - 管理员密码重置（`reset_password`）
     - 角色权限变更（`set_role_permissions` → 遍历持有者）
     - 角色删除（删前记录受影响管理员，删后关联已查不到）
     TTL 300 秒兜底，漏删也会自动恢复。
  5. **内联 `Annotated` 在 `from __future__ import annotations` 下失效**：
     注解被字符串化后，FastAPI 无法在字符串里求值 `require_permission(...)`。
     改用**模块级 Annotated 别名**（如 `AdminModelModelRead`），
     别名在导入时求值，FastAPI 拿到的是对象而非字符串。
  6. **测试夹具的覆盖陷阱**：`get_permission_resolver` 是**工厂**
     （返回 resolver 的函数），覆盖时写
     `app.dependency_overrides[get_permission_resolver] = lambda: resolver`，
     而不是直接覆盖成 async 函数——后者会被 FastAPI 当成依赖去解析参数，
     直接返回 400。
  7. **本次改动的真正意义**：在此之前 B 端**任何管理员都能操作所有功能**，
     `require_admin` 只校验 Token 类型与 `token_version`。
     T05 补上了这层缺失的鉴权。

- 预估工时：2h（实际约 3.5h，主要在批量接入 56 处路由声明）
- 状态：DONE

- 预估工时：2h

- **实现说明（2026-11-08）**：
  1. **存储形式与接口形式不同**：`site_setting` 是键值对表，
     接口返回固定四字段。这层差异由 `setting_service` 吸收——
     路由层拿到的直接是固定字段的 dict。
     键值对的价值在**存储侧**：新增配置项不用改表结构；
     固定字段的价值在**契约侧**：前端可以直接绑定，不用维护 key 常量。

  3. **只返回约定的四个字段**：库里有历史遗留键也不会泄漏到接口。
     用 `[key for key in DEFAULT_SETTINGS]` 过滤。
  4. **PATCH 语义**：`model_dump(exclude_unset=True)` 区分「没传」
     与「显式传 null」。只更新的传入项，其余保持原值。
  5. **缓存 TTL 600 秒 + 主动失效**：配置读取频率高于写入，
     缓存收益明显。更新后立即删键，TTL 只是兜底。
  6. **一个驱动差异**：asyncpg 下 JSONB 列直接返回 Python 对象，
     不需要 `json.loads`；换成同步驱动（psycopg）时会是字符串。
     测试按 asyncpg 的实际行为断言，并在注释里标明这个差异。
  7. **`setex` 已废弃**：Redis 客户端的 `setex(key, ttl, value)`
     被标记为 deprecated，改用 `set(key, value, ex=ttl)`。

- 优先级：P0
- 依赖：M15-T03

- 任务描述：实现管理员登录、登出（全端）、修改自己密码三个接口。

- 交付物：

  - [x] `backend/app/modules/system/auth_service.py` — 认证业务逻辑
  - [x] `backend/tests/unit/test_admin_auth_api.py` — 22 项

- 验收标准（DoD）：

  - [x] 登出后 `admin_user.token_version` 自增（DB 断言）
  - [x] 改密时原密码错误返回 `25007`（400）（接口测试）
  - [x] 改密后原 Token 失效（接口测试）

- 边界与异常：管理员账号禁用后无法登录。

- **实现说明（2026-11-08）**：
  1. **B 端终于有真正的登录接口了**：`/api/v1/admin/auth/*` 之前
     在 `router.py` 里是注释状态，B 端登录页无法工作。本任务补上了。
  2. **登录错误不区分「用户名不存在」与「密码错误」**：都返回
     11006「用户名或密码错误」。区分会让人能枚举系统里有哪些管理员。
  3. **时序侧信道防护**：账号不存在时也跑一次 bcrypt 校验（用固定
     假哈希），让两种情况耗时接近。否则攻击者能通过响应时间判断
     用户名是否存在。
  4. **B 端 Refresh Token 用独立的 Cookie 名**：
     `travel_admin_refresh_token`（C 端是 `travel_refresh_token`）。
     同一浏览器同时登录两端时不会互相覆盖，`path=/api/v1/admin`
     限制只在 B 端接口发送。
  5. **登出不要求权限项**：任何已登录管理员都要能登出。若要求
     `system.xxx` 权限，「没有权限的人反而登不出去」。
  6. **改密与重置密码的区别**：
     - `PUT /admin/me/password`（本任务）：**校验原密码**，
       修改自己的凭据要证明是本人
     - `PUT /admin/system/admins/{id}/password`（T03）：不校验原密码，
       超管重置他人
  7. **改密与登出都自增 `token_version`**：改密码就应假设旧凭据
     可能已泄露，所有设备需重新登录。
  8. **B 端 Token 访问 C 端返回 403 而非 401**：Token 本身有效，
     只是「类型不对」，语义上是禁止而非未认证。测试按 403 断言。

- **实现说明（2026-11-08）**：
  1. **原登录页调用的接口不存在**：`src/pages/Login/index.tsx` 已经写了
     `request({ url: '/auth/login' })`，但后端 `/api/v1/admin/auth/*`
     一直是注释状态。本任务把后端补上后，前端才真正可用。
  2. **store 字段与后端不一致**：原 `AdminUser` 是
     `{admin_id, display_name, role, permissions[]}`，后端实际返回
     `{id, username, real_name, roles[]}`。已全部对齐。
     **不再缓存 permissions**——权限由后端校验，前端缓存一份完整列表
     只会带来「前端说能点、后端说没权限」的不一致。
  3. **会话恢复是新加的关键能力**：Access Token 存内存（评审 §Q1），
     刷新页面即丢失。不做恢复的话，管理员每刷新一次就要重新登录。

     失败静默忽略——首次访问的访客本来就没 Cookie，弹「登录已过期」
     对他们是噪音。
  4. **`RequireAdmin` 必须等恢复完成**：否则刷新页面时，
     恢复请求还没回来就判「未登录」，把已登录的管理员踢回登录页。
     等待期间显示 `Spin`。
  5. **补了后端 `/auth/refresh`**：前端 `http.ts` 的自动刷新逻辑
     引用这个路径，但 B 端没有该接口。不补的话 Access Token
     30 分钟过期后会被直接踢出登录。
     B 端 refresh **不复用 C 端的 `token_service`**——那个查 `user` 表、
     判 C 端状态枚举，硬塞 user_type 参数会让它变成两模块的混合体。
     但**轮换机制复用同一套 Redis jti 黑名单**（与账号体系无关）。
  6. **开放重定向防护**：`?redirect=` 只接受站内相对路径，
     拒绝 `https://evil.com`、`//evil.com`、`/login` 自身。
     有测试覆盖这三种情况。
  7. **登出先调后端再清本地**：`token_version` 自增才能让其他设备
     的 Token 失效。网络异常时仍然清本地状态——否则用户卡在
     「点了没反应」。
