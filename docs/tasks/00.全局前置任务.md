#### [M0-T02] 数据库连接与会话管理

- 所属模块：M0 全局前置
- 优先级：P0
- 依赖：M0-T01
- 关联文档：架构 §1.4、`docs/rules/database-rules.md`
- 任务类型：后端

- 任务描述：建立 PostgreSQL 异步连接（SQLAlchemy 2.x + asyncpg），实现会话管理与事务边界。定义 ORM Base 与通用字段约定（`id` UUID 主键、`created_at`/`updated_at` TIMESTAMPTZ）。**禁止在任何 ORM 模型中声明物理外键**。

- 交付物：
  - [x] `backend/app/db/session.py` — async engine、SessionLocal、`get_db` 依赖
  - [x] `backend/app/db/base.py` — DeclarativeBase、通用 Mixin（id/created_at/updated_at）
  - [x] `backend/app/db/models/__init__.py` — 模型导出入口
  - [x] `backend/app/db/migrations/` — Alembic 初始化配置
  - [x] `backend/tests/integration/test_database.py` — 连接、事务边界、ORM 约定的集成测试

- 验收标准（DoD）：
  - [x] 连接池可建立连接并执行 `SELECT 1`（`TestConnection::test_select_one`，连真实 PG）
  - [x] **规范检查：`grep -rniE 'ForeignKey|relationship\(.*foreign_keys' backend/app/db/models/ backend/app/modules/` 无输出**
    （模型分布在各模块的 `models.py`，检查范围同步扩大）
  - [x] Alembic `upgrade head` 与 `downgrade base` 可重复执行不报错（实测 upgrade → upgrade → downgrade → upgrade 均正常）
  - [x] 主键类型统一为 UUID，命名统一为 `id`（`TestOrmBase::test_primary_key_is_uuid_named_id`）

- 边界与异常：数据库不可达时启动应快速失败并输出连接串（脱敏）；连接池耗尽时的等待与超时策略需明确。

- **实现说明（2026-11-07）**：
  1. **事务边界**（已与用户确认）：`get_db` **不自动提交**，写操作由 service 层显式
     `await session.commit()`；异常时依赖负责回滚。
     理由：自动提交会让「业务校验失败但数据已落库」难以定位；代价是写接口必须记得提交，
     故约定所有写操作收敛在 service 层。已有测试 `test_get_db_does_not_autocommit` 守护该约定。
  2. **`.env` 定位改为绝对路径**：原 `env_file=(".env", "../.env")` 依赖启动时工作目录，
     从项目根目录跑测试会找不到 `backend/.env`。改为基于 `__file__` 计算，任意目录启动均一致。
  3. **Mixin 顺序修正**：`BaseModel(Base, UUIDPrimaryKeyMixin, TimestampMixin)` 改为
     `BaseModel(UUIDPrimaryKeyMixin, TimestampMixin, Base)`，符合 SQLAlchemy 的 MRO 约定。
     原写法虽能工作，但多个 Mixin 叠加时容易出现列覆盖问题。
  4. **测试事件循环作用域**：asyncpg 连接池与事件循环绑定，改为整个测试会话复用同一 loop
     （`asyncio_default_fixture_loop_scope` / `asyncio_default_test_loop_scope = session`），
     否则第二个用例会报 "attached to a different loop"。
  5. **基线迁移为空**：43 张表的建模属于 M0-T13，本任务只验证 Alembic 工具链可用。

- 预估工时：2h
- 状态：DONE

#### [M0-T03] 统一响应封装与全局异常处理

- 所属模块：M0 全局前置
- 优先级：P0
- 依赖：M0-T01
- 关联文档：API §1.3（统一响应结构、HTTP 状态码映射）
- 任务类型：后端

- 任务描述：实现 `{code, message, data}` 统一响应封装与全局异常处理器。定义业务异常基类与错误码枚举，实现参数校验失败（10001）的字段级错误详情输出。

- 交付物：
  - [x] `backend/app/core/response.py` — `success()/error()/validation_error()`
  - [x] `backend/app/core/exceptions.py` — `BusinessError` 基类、错误码分段常量、语义化异常基类
  - [x] `backend/app/core/error_handlers.py` — RequestValidationError、BusinessError、HTTPException、未捕获异常四个处理器
  - [x] `backend/app/schemas/common.py` — `ApiResponse`、`PageData`、`ValidationErrorItem`
  - [x] `backend/app/schemas/pagination.py` — `PageQuery`、`SortQuery`、`build_page()`
  - [x] `backend/tests/unit/test_error_handling.py` — 41 项测试

- 验收标准（DoD）：
  - [x] 参数校验失败返回 HTTP 400 + `code=10001` + `data.errors[]` 含 `field`/`reason`（`TestValidationErrorResponse`）
  - [x] 未捕获异常返回 HTTP 500 + `code=10002`，**不泄露堆栈**（`TestUnhandledException` 断言不含 `Traceback`/异常原文）
  - [x] 规范检查：`grep -rn "HTTPException(" backend/app/ | grep -v core/` 无输出（`TestNoHttpExceptionInBusinessCode` 静态扫描）

- 边界与异常：需处理 Pydantic v2 的 `ValidationError` 结构差异；业务码与 HTTP 状态码映射必须严格按 API §1.3 表执行，不得统一返回 200。

- **实现说明（2026-11-07）**：
  1. **模型与构造函数分离**：响应模型（`ApiResponse`/`PageData`）统一放
     `schemas/common.py`，`core/response.py` 只保留 `success()/error()` 构造函数。
     原来两处各定义了一份分页模型（`core.response.PageResult` 与
     `schemas.pagination.PageData`），已消除重复。分离原因：`core` 是基础设施层，
     不应被 `schemas` 反向依赖；模型收敛到 `schemas` 后 M0-T10 的类型生成有单一来源。
  2. **错误码分段常量**：新增 `ErrorCodeSegment`，完整登记 API §1.7 的 15 个码段，
     并提供 `validate_error_code()`。模块定义常量时可在测试中调用，
     避免「各模块随手编号、码段逐渐失控」。
  3. **语义化异常基类**：新增 `ForbiddenError`、`ConflictError`、`RateLimitedError`，
     `NotFoundError` 改为接受模块自定义错误码（如 M09 传 19001）但 HTTP 状态码固定 404。
     模块继承这些基类即可获得正确状态码，不必查映射表。
  4. **错误码重命名**：`NOT_FOUND`(10004) 改为 `ROUTE_NOT_FOUND`，
     与「资源不存在」（404 + 模块专属码）区分开，避免语义混淆。
  5. **校验错误中文化**：Pydantic 的英文错误按 `type` 映射为中文原因，
     字段名剔除 `body`/`query` 等位置前缀，嵌套字段用点号连接（`address.city`）。
  6. **框架 404 中文化**：Starlette 默认的 `Not Found` 等英文 detail 替换为中文，
     但业务侧显式传入的 detail 原样保留。
  7. **中间件栈验证**：`BaseHTTPMiddleware` 有可能吞掉 `Exception` 处理器，
     故增加 `TestRealApplicationStack`，在真实 `create_app()` 上验证 500 兜底仍生效。

- 预估工时：2h
- 状态：DONE

#### [M0-T04] Redis 客户端封装

- 所属模块：M0 全局前置
- 优先级：P0
- 依赖：M0-T01
- 关联文档：架构 §1.4（Redis 用途）、部署现状（单实例 + DB 0/1 隔离）
- 任务类型：后端

- 任务描述：封装 Redis 异步客户端，支持密码认证与逻辑库选择。**DB 0 供业务使用，DB 1 供 Langfuse 使用**，业务代码只允许访问 DB 0。

- 交付物：
  - [x] `backend/app/infra/redis.py` — 客户端单例、连接池、健康检查、重试、降级判定
  - [x] 提供 `get_redis()` 依赖
  - [x] 业务 DB 常量（DB 0）与注释说明 DB 1 被 Langfuse 占用
  - [x] `backend/tests/unit/test_redis.py` — 16 项单元测试
  - [x] `backend/tests/integration/test_redis_connection.py` — 6 项集成测试

- 验收标准（DoD）：
  - [x] `PING` 返回 PONG（`TestRedisConnection::test_ping_returns_pong`，连真实 Redis）
  - [x] 业务代码请求 DB 1 时抛出明确异常（`TestDbIsolation::test_langfuse_db_rejected`）
  - [x] 规范检查：连接串从配置读取，不硬编码（`grep -rn "redis://" backend/app/ | grep -v config` 无输出，且有静态扫描测试守护）

- 边界与异常：Redis 不可用时服务应降级为直读 PG 而非整体崩溃（架构 §1.6 决策 3）；连接超时与重试策略需配置化。

- **实现说明（2026-11-07）**：
  1. **降级入口显式化**：新增 `is_available()` 与 `RedisUnavailableError`。
     原实现只有 `check_redis()` 返回 bool，业务代码无法区分「Redis 挂了」和「key 不存在」。
     现在调用方模式为：先 `is_available()` 判定，命令失败再捕获 `RedisUnavailableError` 降级读 PG。
  2. **DB 白名单而非只挡 DB 1**：原实现只拦 `db == LANGFUSE_DB`，若有人传 db=2 会悄悄放行。
     改为 `_ALLOWED_DBS = {0}` 白名单，非授权库一律拒绝。
  3. **超时/重试配置化**：新增 6 项配置（连接超时、读写超时、健康检查间隔、
     重试次数、退避基数、key 前缀），原实现把 5s 超时写死在代码里。
  4. **重试策略**：`execute()` 对连接类错误做指数退避 + 抖动重试；
     对 `ResponseError` 等命令语义错误不重试（重试无意义且浪费）。
  5. **key 前缀统一**：`make_key()` 统一加 `travel:` 前缀，避免与同一 Redis 实例上
     的其他系统（Langfuse、其他项目）key 冲突。
  6. **移除 `retry_on_timeout`**：redis-py 6.0 起该参数已废弃（TimeoutError 默认纳入重试），
     改用 `retry_on_error=[ConnectionError, TimeoutError]`。

- 预估工时：1h
- 状态：DONE

#### [M0-T05] JWT 认证中间件与双端隔离

- 所属模块：M0 全局前置
- 优先级：P0
- 依赖：M0-T02, M0-T03
- 关联文档：API §1.2（认证方式）、API §16.3（权限校验矩阵）
- 任务类型：后端

- 任务描述：实现 JWT 签发与校验，Access Token 30 分钟、Refresh Token 7 天。载荷含 `user_type`（`user`/`admin`）与 `token_version`。实现双端隔离中间件：C 端 Token 不可访问 `/api/v1/admin/*`，反之亦然。

- 交付物：
  - [x] `backend/app/core/security.py` — 签发/校验/刷新 Token，bcrypt 密码哈希
  - [x] `backend/app/api/middleware/auth.py` — C 端认证依赖 `require_user()`
  - [x] `backend/app/api/middleware/admin_auth.py` — B 端认证依赖 `require_admin()`
  - [x] `token_version` 比对逻辑（对应用户表该字段）
  - [x] `backend/tests/unit/test_auth_middleware.py` — 31 项测试
  - [x] `backend/tests/integration/test_auth_sql.py` — 5 项 SQL 集成测试（表创建后自动生效）

- 验收标准（DoD）：
  - [x] 无 Token 访问受保护接口返回 401 + `code=11001`（`TestMissingToken`，含空 Bearer、格式错误）
  - [x] C 端 Token 访问 B 端接口返回 403（`TestCrossEndIsolation`，双向都验证）
  - [x] Token 中 `token_version` 与数据库不一致时返回 401（`TestTokenVersion`，含账号不存在、登出后失效）
  - [x] 规范检查：`password_hash`、`api_key` 等敏感字段在响应模型中不出现（`TestSensitiveFieldsNotExposed` 遍历全部 schema）

- 边界与异常：Token 过期、签名错误、载荷缺字段、算法混淆攻击（禁止 `alg=none`）均需覆盖测试。

- **实现说明（2026-11-07）**：
  1. **`token_version` 比对已真正接入**：原实现的 `require_user` 只做 Token 自校验，
     并在注释中说明「DB 比对由业务层补充」——但这正是本任务的核心 DoD，等于未完成。
     现改为每次请求都查询用户表比对（已与用户确认该策略）。
     性能：走 `user.id` 主键索引，单次约 0.1ms，且复用本请求已有的数据库会话。
     不采用 Redis 缓存的原因：缓存会让封禁/登出延迟生效，与 M01-T09 的 DoD 冲突。
  2. **解析器可替换**：`token_version` 查询封装为 `TokenVersionResolver` 依赖，
     测试通过 `app.dependency_overrides` 注入替身，无需建表即可验证认证逻辑。
  3. **强类型载荷**：`decode_token` 返回值从 `dict` 改为 `TokenPayload` dataclass，
     业务层不再重复做 `uuid.UUID(payload["sub"])` 这类转换，也避免拼错键名。
  4. **bcrypt 72 字节限制**：bcrypt 会静默截断超长密码，导致前 72 字节相同的两个密码
     等价。`hash_password` 改为显式拒绝，`verify_password` 返回 False。
  5. **`create_token_pair()`**：登录/注册/刷新三处重复构造双 Token，统一为一个函数。
  6. **禁用账号的处理**：`admin_user.status='disabled'` 与 `user.status='deleted'`
     在 SQL 层过滤，解析器返回 None，最终转为 401。

- 预估工时：2h
- 状态：DONE

  1. **拆分职责**：原实现把中间件放在 `core/logging.py` 里，与交付物清单要求的
     `api/middleware/logging.py` 不符。现拆为「格式器与脱敏规则」+「请求边界采集」两处。
  2. **`request_id` 用 Filter 注入**：原实现只在 `JsonFormatter` 内部读取 ContextVar，
     导致其他 Handler（文件、日志采集器）拿不到该字段。改为 `RequestIdFilter`，
     任何 Handler 都能使用。

     业务代码若写 `logger.info(f"login pwd={pwd}")` 则完全拦不住。
     新增 `redact_message()` 用正则兜底，覆盖 `password=xxx`、`"api_key": "xxx"`、
     `Bearer xxx` 三种常见写法。
  5. **生产环境强制不低于 INFO**：原实现直接使用配置值。新增 `force_info` 参数，

  6. **SQL 日志固定 WARNING**：SQLAlchemy 的 DEBUG 会打印全部绑定参数
     （含手机号、密码哈希），任何环境都不应默认开启。
  7. **请求体不落日志**：只记录 `content-length` 与 UA，中间件不调用
     `request.body()`，避免大文件或敏感内容进入日志。
  8. **探针路径跳过**：`/api/health` 等高频路径不记访问日志，避免刷屏。
  9. **慢请求告警**：超过 1s 的请求日志级别升为 WARNING。
  10. **上游 ID 透传**：支持 `X-Request-ID` 请求头，便于跨 Nginx 追踪。

#### [M0-T12] 统一分页与查询参数辅助

- 所属模块：M0 全局前置
- 优先级：P1
- 依赖：M0-T03
- 关联文档：API §1.4（分页约定）、§1.5（通用查询参数）
- 任务类型：后端

- 任务描述：实现统一的分页请求参数模型与响应构造器，以及通用排序参数（`sort_by`/`sort_order`）校验。页码从 1 开始，`page_size` 默认 20、上限 100。

- 交付物：
  - [x] `backend/app/schemas/pagination.py` — `PageQuery`、`SortQuery`、`CommonQuery`、`build_page()`
  - [x] `backend/app/utils/query.py` — 排序白名单、多字段排序、LIKE 通配符转义
  - [x] `backend/tests/unit/test_pagination.py` — 61 项测试

- 验收标准（DoD）：
  - [x] `page_size` 传 101 时返回 400 + `code=10001`（`test_page_size_101_returns_400_with_code_10001`，真实接口）
  - [x] `page=0` 或负数返回 400（`test_page_zero_returns_400`、`test_page_negative_returns_400`）
  - [x] 响应含 `items/total/page/page_size/total_pages` 五个字段（`test_has_exactly_five_fields` 用 `set()` 精确断言）
  - [x] 规范检查：`sort_by` 走白名单，防止 SQL 注入（6 种注入载荷全部拒绝）

- 边界与异常：`total` 为 0 时 `total_pages` 返回 0 或 1 需统一并写明；深分页（offset 过大）的性能提示。

- **实现说明（2026-11-08）**：
  1. **`total=0` 约定明确为 0**：API §1.4 未规定。选 0 而非 1 的原因：
     前端用 `total_pages === 0` 判断空态比 `total === 0` 更直观，且 `page > total_pages`
     时可以直接判定越界。已在 `build_page` 文档和测试中固化。
  2. **`apply_sort` 默认字段也要过白名单**：原实现未指定 `sort_by` 时直接取
     `model.created_at`，绕过白名单。若默认字段拼错，会抛 `AttributeError`（500）
     而非清晰的 400。现改为默认字段也必须在白名单内，否则明确报错。
  3. **新增 `escape_like()`**：用户搜索 `100%` 时，`%` 被当成通配符会匹配全部记录。
     现转义 `%`、`_`、`\` 三个字符，并提供 `build_like_pattern()` 直接生成安全模式。
  4. **新增 `apply_multi_sort()`**：多字段排序（如「先按状态、再按创建时间」），
     任一字段非法则整体拒绝，不会部分生效。
  5. **新增 `CommonQuery`**：合并分页 + 排序 + `keyword`/`status`，
     B 端列表接口的通用入参（API §1.5），避免每个接口重复定义。
  6. **新增 `is_deep_page`**：`page > 100` 时标记为深分页。PostgreSQL 的 OFFSET
     需要扫描并丢弃前 N 行，深分页性能急剧下降，业务层可据此拒绝或改用游标分页。
  7. **`page_params()` 补齐 `sort_params()`**：原实现只有分页参数，
     排序参数需各接口自己声明，容易写错。

- **附带修复**：`pyproject.toml` 中 B008 的 `per-file-ignores` 从单个测试文件
  扩大到 `backend/**/*.py`——FastAPI 依赖注入要求 `Depends()` 写在参数默认值，
  项目内任何端点都会触发该误报，逐个文件配置不可持续。

- 预估工时：1h
- 状态：DONE

  - [x] `backend/scripts/generate_migrations.py` — 从 schema.sql 生成迁移
  - [x] 迁移脚本与 `schema.sql` 的一致性校验（`TestSchemaConsistency`）
  - [x] 分区表（`model_call_log`、`user_event`）的初始分区创建逻辑
  - [x] `backend/tests/integration/test_migrations.py` — 14 项测试

- 验收标准（DoD）：
  - [x] 在空库执行 `alembic upgrade head` 后，表数量为 **43**（不含分区子表），与 `schema.sql` 一致（**实测**）
  - [x] `alembic downgrade base` 可完全回滚（**实测**，回滚后仅剩 `alembic_version`）
  - [x] **规范检查：生成的 DDL 中无 `FOREIGN KEY` / `REFERENCES`**（grep 无输出 + 测试守护）
  - [x] **规范检查：对照 `docs/rules/database-rules.md` §4.2「禁止使用物理外键」**
  - [x] 所有表主键为 UUID 类型，无 `SERIAL`/`BIGSERIAL`（测试断言每个 `primary_key=True` 必须配 `postgresql.UUID`）
  - [x] 规范检查：表名与字段名为 `snake_case`

- 边界与异常：分区表的 `PRIMARY KEY (id, created_at)` 复合主键；`CHECK` 约束需完整保留；触发器（`updated_at` 自动更新）需在迁移中创建。

- **实现说明（2026-11-08）**：
  1. **采用生成器而非手写**：43 张表、475 个字段、103 个索引、37 个 CHECK、
     118 条注释、28 个触发器，手写既慢又易漏。`scripts/generate_migrations.py`
     从 `schema.sql` 解析并生成声明式 Alembic 代码，保证逐项一致。
  2. **迁移拆分 14 个文件**（已与用户确认方案）：
     `0001_baseline`（pg_trgm 扩展 + 触发器函数）→ 按模块 0002~0014。
     好处：单个文件可读；某模块变更时只重建对应文件。
  3. **原生 SQL 用 `exec_driver_sql`**：注释里的 JSON 示例（`{"ticket":420}`）
     会被 SQLAlchemy 误认为绑定参数（`$1`），`op.execute` 与 `sa.text()` 都会报错。
     改用 `op.get_bind().exec_driver_sql()`，不解析参数标记。
  4. **表名必须加引号**：`user`、`model` 是 PostgreSQL 保留字，
     原生 SQL 里的索引、触发器、DROP 语句都需要 `"user"` 形式。
  5. **分区表声明 `postgresql_partition_by`**：否则后续 `PARTITION OF` 报
     `"model_call_log" is not partitioned`。
  6. **列级 CHECK 作为表级约束**：SQLAlchemy 的 `CheckConstraint` 不接受
     `column=` 参数，改为普通表级约束（表达式里已含列名）。
  7. **`server_default` 必须传字符串**：数字 `0`、布尔 `true` 都要转成
     `'0'`、`'true'`，否则 SQLAlchemy 报类型错误。
  8. **未识别类型直接报错**：原实现静默降级为 `sa.String()`，会丢精度并掩盖问题。
     现在抛 `ValueError` 提示补映射（本次据此补上了 `TIME`）。
  9. **约束行判定用全词匹配**：原 `startswith("CHECK")` 会把
     `checkpoint_id` 这种列名误判为约束行，导致字段丢失。

- **修复的测试污染**：`test_migrations.py` 调用 Alembic 时，`env.py` 的
  `fileConfig()` 会清空 root logger 的 handler，导致同一次 pytest 运行中
  后续用例的 `caplog` 失效（`test_celery.py` 5 项失败）。
  新增 `config.attributes["configure_logger"] = False` 让测试跳过日志接管。

- **实测记录（2026-11-08）**：
  ```
  alembic upgrade head   → 43 主表 / 6 分区子表 / 166 索引 / 28 触发器 / 40 CHECK
  alembic downgrade base → 仅剩 alembic_version，完全回滚
  重新 upgrade head      → 再次成功
  ```

- 预估工时：2h（实际约 6h，主要消耗在生成器调试）
- 状态：DONE
