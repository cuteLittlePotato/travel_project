## 二、结构性偏离（需决策，已确认）

### 2.1 ORM 模型与迁移的关系 —— ✅ 已确认并落地

**问题**：M0-T13 的迁移是从 `schema.sql` 生成的**纯 DDL**，没有配套 ORM 模型。
这导致 `alembic autogenerate` 失效——`Base.metadata` 里没有任何表，
`alembic check` 会把全部 43 张表报告为「应删除」。

更深层的问题是设计文档内部存在矛盾：
- 架构 §4.2：ORM 模型放 `app/db/models/`（按模块划分）
- 架构 §4.3：模块内部分层含 `models.py`

**用户决策**：**模型先行，差异归零后作为唯一真相**

**落地措施**（本次审查实现）：

1. 新增 `app/db/migrations/filters.py`——autogenerate 对象过滤规则
   - 排除分区子表（`*_p2026_*`、`*_default`），ORM 无法表达
   - 排除 `alembic_version`
2. `env.py` 接入该过滤器
3. 新增 `scripts/check_model_drift.py`——每个模块写完模型后核对差异
4. 新增 `tests/unit/test_migrations_filters.py`——13 项测试守护

**后续工作流**：

```
写 ORM 模型（app/modules/<module>/models.py）
  ↓
uv run python scripts/check_model_drift.py --module <module>
  ↓
差异为零 → 模型即真相，后续改表用 autogenerate
有差异  → 「库有模型无」补模型；「模型有库无」确认是设计变更后生成迁移
```

**补充决策（2026-11-08 二次确认）**：

1. **模型位置**：`app/modules/<module>/models.py`，`app/db/models/__init__.py` 只做聚合导入。
   原因：架构 §4.2 与 §4.3 对此存在矛盾，统一到 §4.3 的模块内分层更符合实际。
   已同步修正架构文档 §4.2 与 §4.3。

2. **实施节奏**：跟着模块走，不一次性写 43 张表。
   每个模块开工先写模型 + 跑 drift 检查，差异归零后再写业务代码。
   原因：现在全写无法被真实业务验证，很可能返工。

3. **`--module` 参数落地**：`check_model_drift.py` 新增 `MODULE_TABLES` 映射
   （13 个模块 → 43 张表，无重复无遗漏）。没有这个隔离，
   M01 开工时会看到「M04/M09/M11 的表都没写模型」这类预期内噪音，
   真实问题被淹没。

4. **任务清单修正**：M01-T01（用户表迁移）已由 M0-T13 完成，标记 DONE；
   ORM 模型归属 M01-T02。M0-T02 的外键检查范围从 `app/db/models/`
   扩大到 `app/modules/`。
