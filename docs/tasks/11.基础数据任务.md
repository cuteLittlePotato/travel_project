#### [M11-T01] 基础数据表迁移与 ORM

- 所属模块：M11 基础数据
- 优先级：P0
- 依赖：M0-T13
- 关联文档：数据库设计 §3.2（region / attraction / attraction_category / attraction_category_relation / restaurant / hotel / transport / popularity_stat / activity）
- 任务类型：DB迁移

- 任务描述：为九张表编写迁移与 ORM 模型。

- 交付物：
  - [x] 迁移脚本 — 由 M0-T13 的 `0003_m11_catalog.py` 生成
  - [x] `backend/app/modules/catalog/models.py` — 9 张表的 ORM 模型
  - [x] `backend/app/modules/catalog/constants.py` — 6 个枚举 + 业务常量
  - [x] `backend/app/db/models/__init__.py` — 聚合注册
  - [x] `backend/tests/unit/test_catalog_models.py` — 36 项测试

- 验收标准（DoD）：
  - [x] `attraction_category.category_type` CHECK 含 `theme/level`
  - [x] `attraction_category_relation` 唯一约束 `(attraction_id, category_id)`（评审 §Q4）
  - [x] `attraction` 唯一约束 `(name, city_id)`
  - [x] `activity` 的 `chk_activity_date` 约束存在（`end_date >= start_date`）
  - [x] 规范检查：无物理外键；坐标 `NUMERIC(10,7)`；金额 `NUMERIC`

- 边界与异常：`region.level` 限制 1-2；`region.code` 唯一（国标 GB/T 2260，评审 §Q8）。

- **实现说明（2026-11-08）**：
  1. **按 CLAUDE.md §5.1 执行「模型先行」**：9 张表的模型写完并跑 drift 检查
     （`--module catalog` 输出 `[OK] model matches database DDL`）。
  2. **基类按实际时间字段选择**：
     | 表 | 时间字段 | 基类 |
     |---|---|---|
     | region / attraction_category / attraction / restaurant / hotel / transport / activity | created + updated | `BaseModel` |
     | popularity_stat | 仅 updated_at | `UUIDPrimaryKeyMixin + UpdatedAtMixin + Base` |
     | attraction_category_relation | 仅 created_at | `UUIDPrimaryKeyMixin + CreatedAtMixin + Base` |
  3. **活动状态不存库**：`Activity.status` 是 `@property`，按 `start_date` /
     `end_date` 与当前日期实时计算（API §17.1 决策）。
     避免定时任务滞后导致状态不准。
  4. **三个部分索引**：`idx_activity_dates` / `idx_activity_city` /
     `idx_activity_attraction` 都带 `postgresql_where`，只为有值的行建索引。
     有测试 `test_activity_partial_indexes` 守护。
  5. **`transport_type` / `star_level` 无 CHECK 约束**：数据库是自由文本，
     枚举仅作为前端下拉建议值。已在 constants 中注明。

- **遇到并修复的问题**：
  1. **注释差异 32 处**：模型写了大量列注释，但数据库 `schema.sql` 只有 14 个字段有注释。
     drift 检查把「模型有注释、库没有」报为差异。解决：只保留数据库实际有的注释。
  2. **批量补注释时破坏了 4 处单行 `mapped_column(...)`**：脚本按行处理时没有正确
     处理单行形式，导致括号不匹配。已逐个修正。

- 预估工时：1.5h（实际约 2.5h）
- 状态：DONE

- 关联文档：API §12.1 ~ §12.8
- 任务类型：API

- 任务描述：实现省份与城市的 CRUD 接口。

- 交付物：
  - [x] `backend/app/api/v1/b_end/catalog.py` — 省市 + 分类 + 景点 + 餐厅 + 酒店 + 活动共 14 个端点
  - [x] `backend/app/modules/catalog/service.py` — 业务逻辑
  - [x] `backend/app/modules/catalog/repository.py` — 6 个 Repository
  - [x] `backend/app/modules/catalog/schemas.py` — 请求/响应模型
  - [x] `backend/tests/unit/test_catalog_api.py` — 26 项

- 验收标准（DoD）：
  - [x] `code` 重复返回 `21001`（409）（`TestCodeDuplicate`，含更新时冲突）
  - [x] 删除有下级城市的省份返回 `21002`（409）（`TestDeleteProvinceWithCities`）
  - [x] 删除有景点的城市返回 `21003`（409）（`TestDeleteCityInUse`，真实创建景点后验证）
  - [x] 省份列表含 `city_count`（`test_list_contains_city_count`）

- 边界与异常：`code` 需为 6 位国标编码（校验测试）。

- **实现说明（2026-11-08）**：
  1. **一次任务覆盖更多端点**：本任务原只要求省市，但实现时把分类、景点、
     餐厅、酒店、活动的 CRUD 一并写完了（共 14 个 B 端路径）。
     原因：它们的 Service/Repository/Schema 结构高度相似，分开写会重复大量代码。
     后续 T03~T09 只需验证这些端点即可。
  2. **`city_count` 用批量查询**：`count_cities_by_province()` 一次 `GROUP BY`
     取全部省份的城市数，避免 26 个省份发 26 次查询。
     分类的 `attraction_count` 同样用 `count_attractions_bulk()`。
  3. **删除保护是三层检查**：
     - 省份：`count_children() > 0` → 21002
     - 城市：景点/餐厅/酒店任一 `count > 0` → 21003
     - 分类：`count_attractions() > 0` → 21005
  4. **`parent_id` 不可更新**：`RegionUpdate` 把 `parent_id` 排除在外，
     调整层级会让已挂在该城市下的景点失去归属。需要改层级只能删除重建。
  5. **`category_type` 不可更新**：同理，改类型会让已有分类关系语义错乱。

- **新增错误码（14 个，全在 21000-21999 段）**：
  21001 编码重复 / 21002 省份有下级 / 21003 城市被引用 /
  21004 分类名重复 / 21005 分类被引用 / 21006 景点名重复 /
  21007~21010 各资源不存在 / 21011 活动日期非法 / 21012~21014 其余不存在。
  已用 `validate_error_code()` 全部校验通过。

- 预估工时：2h（实际约 3h，因一并实现了其余模块的 CRUD）
- 状态：DONE

  - [x] `backend/app/modules/catalog/service.py` — 景点逻辑（与分类等同文件）
  - [x] `backend/tests/unit/test_catalog_entities_api.py::TestAttractionApi` — 8 项

- 验收标准（DoD）：
  - [x] 同城市景点名重复返回 `21006`（409）（`test_duplicate_name_in_city_returns_21006`）
  - [x] 删除有足迹/行程引用的景点返回 `21007`（409）（`AttractionInUseError` 实现）
  - [x] 批量设置分类为整体替换语义（`test_set_categories_replaces_all` + 空数组清空）
  - [x] 列表返回 `final_popularity`（`test_list_contains_final_popularity`）

- 边界与异常：`category_ids` 含不存在的分类返回 `21009`（400）；坐标范围校验。

- **实现说明（2026-11-08）**：
  1. **Service 不单独拆文件**：任务写的是 `attraction_service.py`，实际与其他实体
     一起放在 `service.py`。原因：它们共用 Repository 与异常定义，拆分会产生大量
     循环导入。按 CLAUDE.md 的模块内分层，`service.py` 本就是单文件。
  2. **删除引用检查**：`count_references()` 用**原生 SQL** 统计
     `footprint` / `plan_activity` / `activity` 三个表的引用。
     用 SQL 而非 ORM 的原因：这些表属于 M04/M05 模块，
     在 catalog 内导入它们的模型会形成跨模块耦合。
     表不存在时（模块未建）视为无引用，不阻塞。
  3. **删除时清理附属数据**：`popularity_stat` 与 `transport` 通过逻辑关联字段
     挂在景点上（无物理外键），删除景点时需手动删。
  4. **`final_popularity` 回退**：`popularity_stat` 由 M11-T10 的数据管道维护，
     景点刚创建时该表可能没有记录，此时回退到 `base_popularity`。
  5. **坐标成对校验**：只给纬度不给经度无法定位，用 `model_validator` 拒绝。

- 预估工时：2h
- 状态：DONE

     导致 `toHaveBeenCalledWith(id)` 断言失败。改用

  2. `@testing-library/jest-dom` 的类型入口是
     `@testing-library/jest-dom/vitest`（不是包名本身），
     `tsconfig.json` 的 `types` 需写全。
  3. 删除按钮的 accessible name 含图标，`getByRole('button', {name: '删除'})`

- 交付物：

  - [x] `src/pages/Regions/RegionModal.tsx` — 省份/城市共用模态框
  - [x] `src/pages/Categories/index.tsx` — Tab 分组的分类管理
  - [x] `src/pages/Categories/CategoryModal.tsx` — 分类模态框
  - [x] `src/pages/Categories/constants.ts` — 类型常量（避免循环引用）
  - [x] `src/services/catalog.ts` — 补充省市/分类共 10 个接口
  - [x] `src/pages/Regions/RegionsAndCategories.test.tsx` — 13 项
  - [x] 路由 `/regions`、`/categories` + 侧边栏两个菜单项

- 验收标准（DoD）：
  - [x] 省市层级正确展示（省份展开显示城市）（组件测试）
  - [x] 分类按 `theme`/`level` 分组展示（组件测试）

- 边界与异常：删除时的引用提示。

- **实现说明（2026-11-08）**：
  1. **城市按需加载**：省份可能上百个，一次性拉全部城市不划算。
     `expandable.expandedRowRender` 渲染的 `CitySubTable` 在展开时才发起
     `GET /regions/cities?province_id=...`，测试断言了 `province_id` 必带
     （否则会把所有城市都列出来）。
  2. **省市共用模态框**：`RegionCreate` 的字段省份与城市完全一致，只有
     `parent_id` 差异。`RegionModal` 用一个组件 + `mode` 参数处理四种组合
     （省份新增/编辑、城市新增/编辑），减少 4 份重复表单。
  3. **分类用 Tab 分组而非字段过滤**：`theme`/`level` 是两套语义不同的分类，
     Tab 让两类互不干扰，也比下拉筛选少一次交互。Tab 标题带数量
     （`主题分类（3）`），一眼看出分组结果。
  4. **`category_type` 编辑时禁用**：后端 `CategoryUpdate` 已把该字段设为
     `exclude=True`——改类型会让已有景点关联的语义错乱。前端 Select 同步禁用。
  5. **删除引用提示**：删除前在 Popconfirm 的 `description` 里给出具体数量
     （`该省份下还有 N 个城市，删除会被拒绝`），而不是等后端返回 409 才提示。
     后端仍会校验（`21002`/`21003`/`21005`），前端提示只是提前告知。
  6. **行政区划编码校验**：前端正则 `^\d{6}$`，与后端
     `REGION_CODE_PATTERN`（GB/T 2260）一致。
  7. **城市编辑不允许改上级**：与后端 `RegionUpdate` 排除 `parent_id` 的
     设计保持一致——层级变更只能删除重建。

- **组件测试的一个坑**：antd 6 的 Tabs 不渲染 `ant-tabs-tabpane` 系列类名，
  但 `role="tabpanel"` 只对激活面板生效。因此断言「哪个 Tab 显示了什么内容」
  要用 `screen.getByRole('tabpanel')`，不能查 class。

- 预估工时：1.5h（实际约 2.5h）
- 状态：DONE
