#### [M01-T03] 验证码发送与校验服务

- 所属模块：M01 用户与账户
- 优先级：P0
- 依赖：M01-T02, M0-T04
- 关联文档：API §3.1（发送验证码）、需求 §2.1.1
- 任务类型：后端

- 任务描述：实现验证码发送（短信/邮件）与校验服务。验证码存 Redis（DB 0），有效期 5 分钟。实现频率限制：同目标 60 秒 1 次、每日 5 次。

- 交付物：
  - [x] `backend/app/modules/account/verification.py` — 生成、存储、校验、限流
  - [x] `backend/app/infra/sms.py` — 短信发送封装（Mock + 真实对接占位）
  - [x] `backend/app/infra/email.py` — 邮件发送封装（SMTP over SSL）
  - [x] Redis key 命名：`travel:verify:{scene}:{target}` 等 4 种
  - [x] `backend/tests/unit/test_verification.py` — 38 项
  - [x] `backend/tests/integration/test_verification_redis.py` — 6 项（真实 Redis）

- 验收标准（DoD）：
  - [x] 60 秒内重复发送返回 `10003`（HTTP 429）（`TestSendInterval` + 真实 Redis 原子性验证）
  - [x] 每日超过 5 次返回 `10003`（`TestDailyLimit::test_fifth_send_allowed_sixth_rejected`）
  - [x] 验证码错误或过期返回业务异常（`TestVerification`，含过期、错误、跨场景）
  - [x] 规范检查：验证码不在响应体中返回（`TestCodeNotLeaked`，生产环境 `debug_code` 必为 None）

- 边界与异常：短信服务不可用时的降级与提示；同一验证码多次校验失败应作废；`scene` 枚举 `register/login/reset_password`。

- **实现说明（2026-11-08）**：
  1. **Redis key 设计**（4 种，全部带 `travel:` 前缀走业务 DB 0）：
     ```
     travel:verify:{scene}:{target}          验证码明文，TTL 300s
     travel:verify:fail:{scene}:{target}     失败计数，TTL 300s
     travel:verify:rate:{target}:{yyyymmdd}  当日次数，TTL 86400s
     travel:verify:interval:{target}         60 秒间隔占位，TTL 60s
     ```
     第 4 个 key 是为原子性加的：用 `SET NX EX 60` 一条命令完成「检查+占位」，
     避免「先 GET 再 SET」的竞态导致并发下多次发送成功。
  2. **验证码一次性使用**：校验成功立即删除，防重放。
  3. **失败次数上限 5 次**：超过即作废整个验证码。6 位数字只有 100 万种，
     不限次即可被暴力枚举。
  4. **时序攻击防护**：比对用 `secrets.compare_digest` 而非 `==`。
  5. **发送失败回滚**：短信/邮件失败时释放 60 秒锁并回退当日计数，
     避免用户因服务故障被无端锁定（`TestSendFailureRollback`）。
  6. **跨场景共享 60 秒限制**：按 target 计而非 (scene, target)，
     防止换场景绕过限制刷短信。
  7. **`debug_code` 仅开发环境返回**：便于本地联调，生产环境强制为 None。

- **与 API §3.1 的差异说明**：
  API 定义的响应体是 `{"expires_in": 300}`。实现额外返回 `debug_code`，
  但**仅在 `APP_ENV != production` 且 Mock 模式**下。生产环境响应与文档完全一致。

- 预估工时：2h（实际约 2.5h）
- 状态：DONE

  - [x] `backend/app/modules/account/repository.py` — 5 个 Repository
  - [x] `backend/tests/unit/test_register_api.py` — 25 项

- 验收标准（DoD）：
  - [x] 注册成功返回 HTTP 201 + `user_id` + 双 Token（`test_returns_201_with_tokens`）
  - [x] 重复 target 返回 `11003`（HTTP 409）（`test_duplicate_target_returns_409`）
  - [x] 注册后 `user_profile`、`user_setting` 各存在一条记录（`test_creates_profile_and_setting`，DB 断言）
  - [x] 规范检查：`password` 8-32 位含字母数字（5 种非法密码全部拒绝）；响应不含 `password_hash`
        （`test_response_has_no_password_hash` 检查 5 个敏感串）

- 边界与异常：验证码错误 `11004`；target 格式非法 400；事务需保证用户与绑定同时成功。

- **实现说明（2026-11-08）**：
  1. **一次提交保证原子性**：`register()` 在同一个事务内创建
     user + oauth_binding + user_profile + user_setting，最后统一 commit。
     任何一步失败都回滚，不会留下半个账号。
  2. **并发注册兜底**：查重与插入之间存在时间窗，靠数据库唯一索引
     `uk_oauth_provider_uid` 兜底，捕获 `IntegrityError` 转为 11003。
  3. **Username 不暴露 target**：用 `sha256(target)[:12] + 随机后缀` 生成，
     避免用户名泄露手机号。
  4. **默认昵称**：手机号用 `138***8000` 掩码；邮箱用本地部分 + 随机后缀。
  5. **Refresh Token 双写**：响应体返回一份（兼容非浏览器客户端），
     同时写入 httpOnly Cookie（评审 §Q1，`Secure` + `SameSite=Lax` + `Path=/api/v1/auth`）。
  6. **验证码在事务前消费**：若后续创建失败，验证码已失效，用户需重新获取。
     这是刻意设计——避免验证码被反复利用。

- **顺带补充（超出本任务范围）**：
  - `schemas.py` 补齐了后续任务要用的模型（用户资料、偏好、隐私设置）
  - `repository.py` 补齐了 5 个 Repository（用户、绑定、偏好、设置、通知）
  - `POST /auth/verification-codes` 端点（API §3.1）一并实现

  1. `EmailStr` 需要 `email-validator` 依赖，未安装。改用正则校验，

  2. 邮箱正则原先在 `schemas.py` 与 `verification.py` 各定义一份且不一致
     （`{2,}` vs `+`）。统一到 `constants.py`。

#### [M01-T05] 密码登录接口

- 所属模块：M01 用户与账户

- 关联文档：API §3.3
- 任务类型：API

- 任务描述：实现 `POST /api/v1/auth/login`。支持手机号/邮箱/用户名登录，校验密码，返回双 Token。

- 交付物：
  - [x] `backend/app/api/v1/c_end/auth.py::login`
  - [x] `backend/app/modules/account/service.py::authenticate`
  - [x] `backend/app/modules/account/schemas.py::LoginRequest`
  - [x] `backend/tests/unit/test_login_api.py` — 18 项

- 验收标准（DoD）：
  - [x] 正确凭据返回 200 + 双 Token（`test_returns_200_with_tokens`，手机号/邮箱/用户名三种）
  - [x] 账号不存在 `11005`、密码错误 `11006`（**HTTP 状态码统一 401**，见下方决策）
  - [x] 封禁 `11002`（403）、注销 `11007`（403）
  - [x] 连续 5 次错误锁定 15 分钟并返回 `11008`（`TestLoginLock`，含 TTL 断言）

- 边界与异常：错误提示不得区分「账号不存在」与「密码错误」的具体信息泄露（产品层面可保留错误码区分，但 message 需一致）。

- **⚠️ DoD 内部矛盾的决策（2026-11-08 确认）**：
  原 DoD 同时要求「账号不存在返回 11005（404）」和「message 不得区分」，
  两者矛盾——HTTP 404 vs 401 本身就能被用于账号枚举。

  **确认方案：错误码区分，message 与 HTTP 状态码统一**
  | 情况 | 业务码 | HTTP | message |
  |---|---|---|---|
  | 账号不存在 | 11005 | **401** | 账号或密码错误 |
  | 密码错误 | 11006 | **401** | 账号或密码错误 |

  理由：前端可据业务码做埋点区分，而攻击者无法通过响应差异枚举已注册手机号。
  有测试 `test_messages_are_identical` 守护该约定。

- **登录锁定计数的维度（2026-11-08 确认）**：按 **target** 计数存 Redis。
  key：`travel:login:fail:{target}`，TTL 15 分钟。
  优点：实现简单、不污染数据库。缺点：换标识（手机号 vs 用户名）可绕过计数，
  已在文档中记录该已知限制。

- **实现说明（2026-11-08）**：
  1. **三种登录标识**：手机号/邮箱查 `oauth_binding`，用户名查 `user.username`。
     用户名登录时取该用户的主绑定取 `credential`。
  2. **锁定检查在查库之前**：锁定期内直接拒绝，不消耗数据库查询。
  3. **成功即清空失败计数**：`_clear_failures()`，避免历史失败影响后续。
  4. **更新 `last_login_at`**：登录成功时写入，供 M14 用户分群的「沉默用户」判定使用。
  5. **无密码账号的处理**：验证码自动注册/第三方登录创建的账号 `credential` 为空，
     密码登录返回 11006 而非崩溃。
  6. **日志脱敏**：`_mask_target()` 把手机号转 `138****8000`、邮箱转 `us***@x.com`，
     避免登录日志泄露用户标识。

- 预估工时：1.5h（实际约 2.5h）
- 状态：DONE

- 任务类型：API

  - [x] `backend/app/modules/account/token_service.py` — 轮换机制
  - [x] Refresh Token 黑名单（Redis `SET NX EX`）
  - [x] `backend/tests/unit/test_refresh_token_api.py` — 19 项

- 验收标准（DoD）：
  - [x] 有效 Refresh Token 返回新双 Token（`TestRefreshSuccess`）
  - [x] 旧 Refresh Token 再次使用返回 `11010`（401）（`TestRotation`）
  - [x] 账号封禁状态下刷新返回 `11002`（`test_banned_account_cannot_refresh`）

- 边界与异常：Refresh Token 过期、`token_version` 不匹配均返回 401。

- **实现说明（2026-11-08）**：
  1. **轮换用 jti 黑名单**：JWT 载荷新增 ``jti`` 声明（每次签发唯一）。
     刷新时用 ``SET NX EX`` 原子地把 jti 写入 Redis 黑名单：
     - 首次成功 → 返回 True，继续刷新
     - 重复出现 → 返回 None，判定为重放，拒绝
     有测试 `test_concurrent_refresh_only_one_wins` 验证 5 个并发只有一个成功。
  2. **为什么存 jti 而非 Token 全文**：Token 可能有几百字符，jti 只有 32 字符，
     Redis 内存占用小一个数量级。
  3. **为什么用黑名单而非白名单**：白名单要为每个有效 Token 存一条记录，
     用户量上去后内存压力大。黑名单只存「已被使用过」的，正常使用下数量很少。
  4. **Redis 不可用时拒绝刷新**（503）：无法保证轮换的原子性，
     放行会导致旧 Token 可重放。用户重新登录即可恢复。
  5. **Token 来源双通道**：优先请求体（非浏览器客户端），
     为空时回退到 httpOnly Cookie（浏览器，评审 §Q1）。
     有测试 `test_body_takes_priority_over_cookie` 验证优先级。
  6. **响应不含 user_id**：API §3.6 定义只有三个字段，
     前端已有用户信息，不需要重复返回。

- **配套改动**：`core/security.py` 的 `_create_token()` 新增 `jti` 声明。
  所有新签发的 Token（Access 与 Refresh）都带 jti，但只有 Refresh 的 jti 参与轮换。

- **实现说明（2026-11-08）**：
  1. **路由组实现守卫**：把 chat/plans/footprints/profile 四个页面移到
     `src/app/(protected)/` 目录，`layout.tsx` 统一包裹 `RequireAuth`。
     Next.js 路由组不影响 URL——`/plans` 仍是 `/plans`。
     好处：一次配置覆盖全部受保护页面，新增页面只需放进该目录。
  2. **必须等 `hydrated` 再判断**：登录态来自 httpOnly Cookie 的**异步探测**。
     若探测未完成就判定「未登录」，已登录用户会看到瞬间跳转闪烁。
     `RequireAuth` 在 `hydrated=false` 时显示加载态，不跳转也不渲染内容。
  3. **未登录不渲染任何内容**：即使马上要跳转，也不渲染受保护内容——
     避免用户看到一瞬间的敏感数据。
  4. **redirect 参数**：跳转登录页时带上原路径
     （`/login?redirect=%2Fplans`），登录后可跳回。

- **修正的问题**：`useAuthBootstrap` 原假设 `/auth/refresh` 返回 `user` 字段，
  但 API §3.6 只返回三个字段（`access_token` / `refresh_token` / `expires_in`）。
  已改为两步：先 refresh 拿 token，再用 token 请求 `/users/me` 拿用户信息。
  用户信息请求失败不阻塞登录（用占位 `user_id`），避免网络抖动导致登录态丢失。

- **刷新锁的实现**（`http.ts` 原有）：
  ```typescript
  refreshPromise ??= refreshAccessToken().finally(() => { refreshPromise = null; });
  const newToken = await refreshPromise;
  ```
  `??=` 保证并发 401 只有一个刷新请求，其余等待同一个 Promise。
  `.finally` 保证刷新完成后释放锁，下次 401 可重新触发。
  有测试验证「并发 4 次只调用 1 次刷新」。
